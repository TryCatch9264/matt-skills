## 它做什么

`tdd` 先写测试再实现功能或修缺陷：一个失败的测试，然后刚好够让它通过的代码，然后下一个行为。它带着那些让这个循环产出值得留下的测试的标准：什么算好测试、测试放在哪里、mock 有什么用，以及三种让整个套件变得没有价值的反模式。

它不会在你没有事先同意的接缝上写测试。在任何测试存在之前，它点名打算测试的公开边界，然后停下来等你确认。测试精力是有限的，这一步把它花在关键路径上，而不是每个边界情形上。`tdd` 也是一份**参考**，不是驱动器。它包含循环的规则，由别的东西（你，或者 [implement](https://aihero.dev/skills-implement)）跑那场应用它们的[会话（session）](https://www.aihero.dev/ai-coding-dictionary/session)。

## 什么时候用它

打 `/tdd`，或者在任务合适时由[代理（agent）](https://www.aihero.dev/ai-coding-dictionary/agent)自动取用：先写测试地实现一个功能或修一个缺陷，或者你说“红-绿-重构”的时候。

当有一个具体行为要建、它有输入和可观察的输出，而你想要经得住重构的测试时用它。

| 你的处境 | 去哪里 |
| --- | --- |
| 一个有明确输入输出的行为（业务逻辑、请求／响应契约、一次转换、校验） | `tdd` |
| 行为还定不下来 | [to-spec](https://aihero.dev/skills-to-spec)，它在写任何代码之前也把测试接缝商定好 |
| 真正的问题其实是接口的形状，不是测试 | [codebase-design](https://aihero.dev/skills-codebase-design) |
| 你有一份[规格说明（spec）](https://www.aihero.dev/ai-coding-dictionary/spec)或[工单（ticket）](https://www.aihero.dev/ai-coding-dictionary/ticket)，想让整个构建替你跑 | [implement](https://aihero.dev/skills-implement)，它每张工单驱动 `tdd` |
| 配置、接线、胶水代码、类型标注、直白的 CRUD 转发 | 这里哪个都不太合适；见下面的已知缺口 |

最后那一行是真实的缺口。技能决定接缝放在*哪里*，但里面没有任何东西判断一个改动值不值得跑这个循环。如果你在一个没有独立事实来源可供断言的改动上用它，你得到的是一个复述实现的测试。那就是技能自己警告的同义反复反模式，只是从另一个方向到达。它是[议题 #746](https://github.com/mattpocock/skills/issues/746)，仍未关闭。在它关闭之前，这个判断你自己做，或者把规则写进你的 `CLAUDE.md`。

## 前提条件

需要装了 [codebase-design](https://aihero.dev/skills-codebase-design)。`tdd` 以前自带深模块和接口设计的说明；v1.0 把它们删掉，改用那个共享技能，`tdd` 现在用它的接口设计词汇。别的都不需要；这个技能是[无状态](https://www.aihero.dev/ai-coding-dictionary/stateless)的，不写自己的文件。

## 循环，以及它跑在什么接缝上

技能建立在三个术语上。

**红-绿。** 写失败的测试，然后只写刚好让它通过的代码。不要为再下一个测试写代码。没有重构阶段。技能在 2026 年 6 月把它去掉了，因为代理几乎从不执行它，而且审查和实现分成不同会话效果更好。重构属于 [code-review](https://aihero.dev/skills-code-review)。

**纵向切片。** 在一个接缝上写一个测试，然后最小实现，再重复。第一个循环是一颗**曳光弹**，证明一条路径端到端可行。反面是横向切分：先写所有测试，再写所有代码。成批写的测试验证的是*想象出来的*行为。它们检查东西的形状而不是用户做什么，而且在还没理解实现之前就把你锁定在某个测试结构上。

**事先商定的接缝。** 接缝是你观察行为而不必伸进内部的公开边界。这条规则没有例外。没有测试放在未确认的接缝上。在完整链条里，接缝更早就在 [to-spec](https://aihero.dev/skills-to-spec) 阶段商定：“`/tdd` 被告知只在事先商定的测试接缝上工作，`/code-review` 检查只用了商定过的测试接缝。”单独调用时，`tdd` 直接问你。

它写出来要防的三种反模式：

| 反模式 | 判断特征 |
| --- | --- |
| 与实现耦合 | 你重命名一个内部函数，行为没变，测试却坏了。mock 内部协作者、断言调用次数、用数据库查询来验证而不是走接口。 |
| 同义反复 | 期望值按代码计算的方式算出来，所以测试由构造方式保证通过。期望值必须来自别处：一个已知正确的字面量、一个算好的例子、规格说明。 |
| 横向切分 | 在任何实现之前落地了一批测试。 |

mock 只用于系统边界：外部 API、时间、随机性，有时是文件系统或数据库。绝不要 mock 你自己的模块。

## 常见问题

**它为什么不重构？描述里写着“红-绿-重构”。**

因为重构那一步被移除了，而描述没改。移除是有意的。代理几乎从不执行那一步，而把实现和审查留在不同会话里效果更好。结果是否还按教科书算 TDD，不如这个循环是否产出更好的代码重要。触发词和正文的不一致已记为[议题 #589](https://github.com/mattpocock/skills/issues/589)，仍未关闭，所以“红-绿-重构”仍然能作为触发技能的说法使用。你得到的是红-绿，重构在 [code-review](https://aihero.dev/skills-code-review) 里。

**它要我自己选一个测试接缝，我完全不知道该选哪个。**

这是关于这个技能被报告最多的摩擦（[议题 #607](https://github.com/mattpocock/skills/issues/607)）。提示只按名字列出候选接缝，不说什么接缝能抓住什么、漏掉什么，所以你是在几个标签之间选。还没有修法发布。实际的变通是回答之前先向代理要取舍：组件级接缝漏掉什么、集成接缝抓住什么、慢多少。这也是链条在 `to-spec` 里提前商定接缝的原因，那里你能看到整个功能，而不只是一个提示。

**它先写了实现再写测试，尽管技能说先红。**

确实会发生。一位用户在这一点上追问[模型（model）](https://www.aihero.dev/ai-coding-dictionary/model)，得到了一个异常诚实的回答：“我知道技能说‘一次一个测试，看着它因为正确的原因失败’。我读了。我只是默认回到我的习惯。”技能接受这一点。没有任何指令能让代理百分之百遵守，而更严的措辞会限制代理的创造力，收益很小。即使代理没严格照做，这个循环仍然值得跑，因为总体结果还是更好。如果某个切片上严格遵守很重要，那就盯着这次运行，别指望技能去强制。

**它该先写浏览器测试或端到端测试吗？**

通常不该，而技能也不会拦住它。一位用户报告代理先写了一个 Playwright 测试，然后花了很长时间反复重跑它，最后断定是*测试*坏了，而那个功能还不存在。浏览器测试慢到红-绿反馈循环已经不划算。在你仓库的 `CLAUDE.md` 里说明浏览器测试放在行为可用之后。

**`/tdd` 会取代 `/implement`，或者课程里的 `/do-work` 吗？**

不会。`/tdd` 记录的是方法论；`/implement` 是一个简单的 工作→反馈→提交 循环，是 `/do-work` 的直接替代。课程里单个 `/do-work` 步骤现在拆成 `/implement`、`/tdd` 和 `/code-review`。如果你在问该对一张工单跑哪个，答案几乎总是 `/implement`。

**深模块和接口设计的指引去哪了？**

v1.0 里进了 [codebase-design](https://aihero.dev/skills-codebase-design)，并做了一般化，让几个技能共用一个词汇。`refactoring.md` 同时离开了；重构现在是 [code-review](https://aihero.dev/skills-code-review) 的活，那个技能带着 Fowler 的坏味道基线。

**它知道我其他的工单吗？**

不知道。对着一张工单跑，它可能提出属于兄弟工单的工作，因为它看不到议题图的其他部分（[议题 #129](https://github.com/mattpocock/skills/issues/129)）。这不是 `tdd` 的活。把规格说明和工单一起传进来有帮助；一开始就把工单切到合适大小帮助更大。

## 它在生效的表现

- 在任何测试文件存在之前，它停下来点名打算测试的接缝，然后等。
- 一个测试出现、变红、得到刚好够的代码变绿，然后才出现下一个测试，而不是一批测试后面跟一批代码。
- 测试名字读起来像能力（“用户能用有效购物车结账”），而不像内部结构（“checkout 调用 paymentService.process”）。
- 断言里的期望值是你追得到规格说明的字面量，而不是按代码计算方式重算出来的值。
- 重命名一个内部函数，套件里什么都不坏。
- mock 只出现在外部边界（支付 API、时钟），绝不围绕你自己的模块。

## 它在哪里合用

`tdd` 跑在主链的构建步骤内部；它不是自己单独的一步：

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

[to-spec](https://aihero.dev/skills-to-spec) 提前商定测试接缝，[implement](https://aihero.dev/skills-implement) 每张工单驱动 `tdd`，[code-review](https://aihero.dev/skills-code-review) 事后检查只用了商定的接缝，并接手 `tdd` 不再做的重构。另一个邻居是 [codebase-design](https://aihero.dev/skills-codebase-design)，接缝和深模块词汇的共同出处，`tdd` 用的就是它。你也可以单独用它，只要有一个具体行为要建、又没有完整规格说明在起作用。不确定哪个技能适合你的处境时，[ask-matt](https://aihero.dev/skills-ask-matt) 会帮你导航。
