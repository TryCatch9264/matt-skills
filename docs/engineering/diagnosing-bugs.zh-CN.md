## 它做什么

`diagnosing-bugs` 对难缠的缺陷或性能退化跑一套六阶段诊断：建立复现、最小化、给假设排序、加观测、带回归测试修复、清理。

在**紧**的反馈回路存在之前，它不让代理形成理论：一条点得出名字的命令，已经跑过一次，能对*这个*缺陷变红、修好后变绿。拿到一份缺陷报告，编码代理默认会读代码然后猜。这个技能挡住这种做法。没有能变红的命令，就没有阶段 2。这道关卡就是这个技能的意义所在。回路一旦存在，之后的一切（二分、假设检验、加观测）都是机械活。

## 什么时候用它

打 `/diagnosing-bugs`，或者在任务合适时由代理自己取用。它是模型调用的，遇到“诊断”、“调试一下”这类说法，或者收到某样东西坏了、抛错、失败、变慢的报告时触发。

难缠的那些用它：一眼解不出的缺陷、时有时无的间歇故障、在两个已知良好状态之间引入的退化。它有意做得慢而彻底，所以对一个你想一条消息就问完的问题，它是错的工具。

| 你的处境 | 去哪里 |
| --- | --- |
| 一个你能描述成症状的具体缺陷 | 本技能 |
| 一个慢的接口，或者一次有已知前后对比的耗时退化 | 本技能。它有性能分支（先测基线，再二分） |
| “这个代码库的瓶颈在哪”，没有具体症状 | 不是这个技能。它诊断一个已知失败，不做审计 |
| 别人发来的原始缺陷报告，还没确认也没写成工单 | 先 [triage](https://aihero.dev/skills-triage) |
| 用一次性代码回答设计问题，不是追缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 先写测试地建一个计划好的行为 | [tdd](https://aihero.dev/skills-tdd) |
| 想知道是什么本该防住这个缺陷（在修好之后） | [retro](https://aihero.dev/skills-retro)，在同一次会话里跑 |
| 没有合适的接缝把这个缺陷固定住 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)，由你自己发起 |

## 紧的回路就是技能本身

阶段 1 投入最多，因为它是唯一困难的阶段。技能列出了构造回路的方式，大致按偏好排序：

1. 在任何能触达缺陷的接缝上写一个失败测试。
2. 对运行中的开发服务器写一个 curl 或 HTTP 脚本。
3. 一次命令行调用，配一份固定输入，与已知正确的快照做 diff。
4. 一个无头浏览器脚本，对 DOM、控制台或网络做断言。
5. 一次重放捕获：保存下来的请求、载荷或事件日志，在隔离环境里沿代码路径跑一遍。
6. 一个一次性测试装置：系统的最小子集，一次函数调用。
7. 属性或模糊测试循环，用于“有时输出错误”。
8. 一个可以交给 `git bisect run` 的二分测试装置。
9. 差分循环：同一输入，旧版本对新版本。
10. 一个[人在环路里（human-in-the-loop）](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)的 bash 脚本，最后手段。技能为此带上了 `scripts/hitl-loop.template.sh`：代理运行脚本，你在终端里按提示操作，你的回答以可解析的输出回来。

目标不是*一个*回路，而是**紧**：快（秒级）、确定（每次运行结论相同）、锐利（断言你的确切症状，不是“没崩”）、代理能不需要你而运行。30 秒还不稳定的回路比没有好不了多少。对只在某些时候出现的缺陷，目标不是干净的复现，而是**更高的复现率**：反复触发、并行、加压、注入等待，直到这个间歇故障的比率高到可以调试。

当代理造不出来时，技能让它停下来直说，列出试过什么，并向你要[环境（environment）](https://www.aihero.dev/ai-coding-dictionary/environment)访问权、一份捕获的产物，或者添加临时观测的许可。它不能就此接着去提假设。

## 阶段之间的关卡

阶段是关卡，不是检查清单。条件不成立，代理就进不了下一个阶段。

| 关卡 | 必须成立什么 |
| --- | --- |
| 进入阶段 2 | 一条点得出名字的命令，已经运行过并连同输出粘贴出来，能对这个缺陷变红 |
| 进入阶段 3 | 复现已复现*并*最小化：剩下的每个元素都是复现所必需的 |
| 进入阶段 4 | 有 3 到 5 个排序的、可证伪的假设，每个都说出自己的预测，并在测试任何一个之前给你看过 |
| 进入阶段 5 | 探针对应具体预测，一次一个变量，每条调试日志都带 `[DEBUG-a4f2]` 这样的标签，好让收尾时一次 grep 全找出来 |
| 完成 | 原始复现不再出现、观测代码已移除、提交信息点出最终被证明正确的假设 |

阶段 5 有一个例外。代理先写回归测试再修，但前提是存在**正确的接缝**：测试能在调用点按缺陷实际发生的方式跑到真实的缺陷模式。如果唯一可用的接缝太浅，技能让代理直说，而不是写一个给出虚假信心的测试。缺少接缝本身就是一条发现，代理记录它，而不是藏起来。

## 常见问题

**我一问简单问题它就触发，我只想直接要个答案。**
这是关于这个技能被报告最多的问题。尤其在 GPT-5.6-Sol 上，用户报告它对一个平实的问题描述就触发：“模型转而触发那个相当正式的 diagnosing-bugs 技能。然后它继续构造一个复现场景（常常是建一个价值有限的 mock 场景），然后才给我回答或建议。这导致回复明显延迟。”有四个人在[议题 #578](https://github.com/mattpocock/skills/issues/578) 上报告了同样的问题。被接受的修法是先走更轻的办法，只在问题需要时才转向完整诊断，但那个改动还没发布。技能是照 Claude Code 的调用行为调的，而触发门槛更低的[模型（model）](https://www.aihero.dev/ai-coding-dictionary/model)会触发得太频繁。在修法发布之前，变通办法是说清你要什么（“直接回答这个，不要诊断”），或者在你的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness) 里关掉它的模型调用。

**我能把它指向一个代码库，问性能问题在哪吗？**
不能。它诊断一个你已经能点出名字的失败。它的性能分支是给有症状的退化用的（建立基线测量，然后二分，先测量后修），不是主动扫一遍。做主动版本的技能被[提过又关掉了](https://github.com/mattpocock/skills/issues/431)；现在没有技能做这件事。

**它写修复之前会停下来问我吗？**
不会。只有阶段 3 有个人工检查点：排序后的假设清单在测试任何一个之前给你看，你若不在场，代理按自己的排序继续。加观测和修复之间没有关卡，所以代理可能在你还没认同它的根因时就开始写代码。[议题 #124](https://github.com/mattpocock/skills/issues/124) 要求这道关卡，仍未关闭。如果你想要，调用技能时说出来。

**我已经对这份缺陷报告跑过 `/triage` 了。这是重复的活吗？**
部分是，而两个技能都不说明这一点。正如一位读者说的：“分诊的第 3 步本质上就是 diagnosing-bugs 阶段 1 到 2 的浅层受限版本，但两个文件都不提对方。”分诊做一遍有边界的“这到底是不是缺陷、表面是什么”的检查；这个技能做彻底版本。先跑分诊不是浪费，因为它的验证常常给你阶段 1 的大部分原料。但要预期这个技能会完整重做那部分，而且不会有交叉引用告诉你。

**它粘贴的复现输出会泄露密钥吗？**
有可能。技能让代理粘贴调用方式和它的输出，还要索取 HAR 文件、日志转储、核心转储这类产物。没有任何指令让代理对它们脱敏。[议题 #674](https://github.com/mattpocock/skills/issues/674) 正是提这件事（凭据、词元、cookie 和个人数据被复制进聊天、议题或 PR），并提议一道脱敏护栏。它仍未关闭、未实现。目前就把脱敏当成你自己的活，尤其是输出要去任何公开地方之前。

**我的安全扫描器把这个技能标为高风险。**
Snyk 标了，而这是误报。它是这套技能里唯一带着可执行 shell 脚本（`hitl-loop.template.sh`）、同时又带运行它的说明和 curl 开发服务器说明的技能。一个随包发布的 `.sh` 文件、运行它的说明，加上对外 HTTP 请求，合起来足以触发静态扫描器。脚本本身大约 30 行的 `read -r -p` 提示，只是停下来等人输入。扫描器评的是这个技能可能做什么，不是已证实的利用方式。

**`/diagnose` 呢？**
v1.0.0 把它改名为 `/diagnosing-bugs`。旧名字不再存在。你自己任何串联 `/diagnose` 的东西（一个包装技能、一条保存的提示）都需要更新。

## 它在生效的表现

- 它先给你看一条命令和它变红的输出，然后才提一个理论。如果理论先到，技能就没在跑。
- 它复现的失败是你报告的那个，不是顺手发现的邻近某个。
- 它在开始猜之前先缩小复现，而且能告诉你为什么还需要剩下的每一块。
- 它给你一份 3 到 5 个假设的排序清单，每个都带一个你可以证伪的预测，然后才逐个测试。
- 它加的每条调试日志都带 `[DEBUG-a4f2]` 这样的标签，声明完成时 grep 那个标签是空的。
- 提交或 PR 信息点出哪个假设是对的。
- 当它无法用测试把缺陷固定住时，它直说，而不是写一个浅的。

## 它在哪里合用

`diagnosing-bugs` 是一个随时可用的独立技能。有东西坏了你就启动它，修复和它的回归测试到位它就结束。它不保留状态，不需要事先配置。[ask-matt](https://aihero.dev/skills-ask-matt) 会把“有东西坏了”这种情况导到这里。

两个邻居要紧。[retro](https://aihero.dev/skills-retro) 在它之后：修复到位后，在同一次会话里跑它，问是什么本该防住这个缺陷，那时会话掌握的信息比开头多。`diagnosing-bugs` 从不自己调用 `retro`，因为 `retro` 是用户调用的。[triage](https://aihero.dev/skills-triage) 在它之前，针对别人发来的原始报告，做同样前两个阶段的浅层版本。
