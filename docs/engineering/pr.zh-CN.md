## 它做什么

`pr` 定义一份拉取请求正文的形态：用**摘要**展示改动，用**证据**说明它有效，用**合并风险**给出落地风险判断。它是格式参考，不是工作流。它不推分支、不开 PR、也不决定里面写什么。它告诉[代理（agent）](https://www.aihero.dev/ai-coding-dictionary/agent)写正文时该长什么样。

摘要是图，不是段落。默认的 PR 正文用散文描述 diff。这个用**最小的视图**把要点讲清（伪代码、调用树、组件树、文件树、Mermaid 图，或者塑形过的 diff），周围的文字保持简短。审查者本来就开着 diff，所以正文让他们在读之前先看到它的形状。

## 什么时候用它

打 `/pr`，或者在代理写 PR 正文时自动取用。

| 你的处境 | 用 |
| --- | --- |
| 分支准备好了，需要一份审查者能扫一眼的正文 | `pr` |
| 代码写完了但还没人审查 | 先 [code-review](https://aihero.dev/skills-code-review)，再 `pr` |
| PR 已开，审查意见正在回来 | 这套技能里暂时没有对应的；`pr` 只写正文 |

## 模板

三节，按这个顺序：

- **摘要**：一个或几个小视图，每个都放在它所支撑的那几行文字旁边。用一种，有时用几种，很少全用上。只保留审查者需要的调用、文件、props 和边界。
- **证据**：改前和改后。改动是视觉上的、且[环境（environment）](https://www.aihero.dev/ai-coding-dictionary/environment)支持截图时，截图是最强的证据。否则就用那个从失败变为通过的测试，写成伪代码，或者用变化了的控制台输出。
- **合并风险**：这个改动是**单向门**还是**双向门**，以及它的**影响面**。双向门回滚成本低；单向门不是（破坏性迁移、删除公开 API、难以撤销的决定）。影响面点出改动出错时可能坏掉的东西：布局错位、API 的调用方、移动端响应式表现。

门的判断是这里的领头想法。它把“这个合进去安全吗”从直觉变成一条明说的主张，审查者可以不同意。它也告诉审查者该把[人工审查（human review）](https://www.aihero.dev/ai-coding-dictionary/human-review)花在哪里。影响面小的双向门扫一眼，单向门慢慢读。

## 常见问题

**我能相信代理自己做的门的判断吗？**

不要盲信，而把这一点说出来正是目的。写这个改动的代理也是给它打分的那一个，所以它说“双向门、影响面小”时最该怀疑。diff 也常常掩盖一个改动到底能不能撤销。正如一位用户说的，“回滚一个提交不会撤回已经发出的一批邮件”，而被标记的灰度发布只有在第一次以新格式写入落地之前才是双向的。技能给代理的是一个定义（破坏性操作和难以撤销的决定属于单向门），不是一张清单，所以合并风险那一行要最仔细地看。两个做法有帮助：确保代理面前有[工单（ticket）](https://www.aihero.dev/ai-coding-dictionary/ticket)或[规格说明（spec）](https://www.aihero.dev/ai-coding-dictionary/spec)，而不只是 diff；并把你们仓库一贯当作单向门的改动（数据库结构迁移、任何对外发布或删除的东西）写在代理做判断之前会读到的地方。

**它会替我开 PR 吗？**

不会。`pr` 只覆盖正文。[implement](https://aihero.dev/skills-implement) 最后是提交到当前分支。要求一个能开 PR 的技能或选项（一个 `/to-pr`，或者让 `implement` 开 PR 而不是提交）目前还是未实现的提议。有用户的做法是在本地用一句话覆盖 `implement`，让它去开 PR。[implement-spec](https://aihero.dev/skills-implement-spec) 是例外：当你的议题跟踪器通过 PR 关闭工作、或者你主动要求时，它会开一个草稿 PR。因为 `pr` 是模型调用的，你让代理去开 PR 时，它就会用这个形态来写正文。

**它不会又产出一堆文字和图吗？**

这个技能就是为防止那个而设计的，但仍然可能发生。用户对代理写的 PR 正文的抱怨很一致：“摘要很长，但我只需要知道改了什么、怎么验证的、可能坏什么、合进去安不安全。”技能让代理跳过前言、保持文字简短、挑最小的视图，通常一个，很少全用。如果你还是收到一串图，那就是代理没照做。如果正文巨大是因为 diff 巨大，那问题在 PR 的大小，`pr` 不会替你拆。

**我的仓库已经有 PR 模板了。哪个优先？**

默认都不，或者说分不出高下。`pr` 有自己的模板，不会去找 `.github/pull_request_template.md` 之类的东西。有用户要求过让技能用仓库的模板。如果你什么都不做，代理对同一份文档就有两套互相冲突的指令。在你们仓库的代理文档里把这件事定下来，例如填好仓库模板，再把摘要、证据和合并风险放在它下面。

**输出是 HTML 吗？为什么 Mermaid 图渲染不出来？**

输出是 Markdown 的 PR 正文，不是 HTML 页面。GitHub 和 GitLab 会在 PR 描述里渲染 Mermaid 块，但终端不会，所以代理在本地给你看的时候，图看起来就是原始文本。用命令行工具的用户用 ASCII Mermaid 渲染器绕过这一点，或者让代理给 PR 附一份 HTML 版本。Mermaid 只是六种视图之一。调用树、文件树或塑形 diff 在哪里读起来都一样。

**它能处理回来的审查意见吗？**

不能。它写完正文就停。用户不止一次要求能对其他开发者或审查机器人留下的评论做分诊（哪些值得处理、哪些不是问题）。这个技能不做这件事。

**PR 变化时它会更新正文吗？**

不会。它在某个时间点写正文，PR 在审查中发生变化后，那份正文就过时了。大的改动之后让代理重写正文。代理又是在写 PR 正文，所以它用同一个形态。

**我的改动没有界面。证据该放什么？**

除截图之外的一切。只有当改动是视觉上的，截图才是最强证据。对迁移、后台任务或重构，证据是那个改之前失败、现在通过的具体测试，或者变化了的控制台输出。单说“测试全绿”是一个主张，不是改前改后。

**它能标明正文是 LLM 写的吗？**

它自己不能。有用户的做法是在仓库的代理文档里放一条常设指令：代理写的每个议题、评论和 PR 都以一行披露结尾。这条规则属于仓库，因为它覆盖代理发布的一切，而不是放在某一种文档的模板里。

## 它在生效的表现

- 光看摘要里的图，不开 diff 就知道这个 PR 改了什么。
- 正文没有前言：直接从摘要标题开始。
- 证据一节给出改前和改后，而不是一句“测试通过”。
- 每个 PR 都说明是哪种门、影响面多大，而你会慢下来读的是那些单向门。

## 它在哪里合用

当构建以拉取请求的形式交付时，`pr` 位于审查和复盘之间：`to-spec → to-tickets → implement → code-review → pr → retro`。它是模型调用的，所以在这条链之外，代理每次写 PR 正文时它也会自己触发。

- [code-review](https://aihero.dev/skills-code-review) 跑在它之前，因为 PR 正文应当描述一个已经被审查过的 diff。
- [implement](https://aihero.dev/skills-implement) 产出正文所描述的提交。

不确定当前情况适合哪个技能时，[ask-matt](https://aihero.dev/skills-ask-matt) 会带你在这整套技能上导航。
