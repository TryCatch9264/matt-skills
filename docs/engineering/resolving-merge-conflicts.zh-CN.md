> **已归档。** 这个技能在 v1.3.0 里从插件中移除了，不再维护。也没有替代品：合并或变基冲突现在由代理自己处理，没有专门的技能。本页留作参考。

## 它做什么

`resolving-merge-conflicts` 逐个 hunk 处理进行中的 git 合并或变基，然后跑项目自己的检查，最后用一次提交把操作收尾。

它拒绝把冲突当成文本问题。动任何一个 hunk 之前，它先把两边都追溯到各自的**[一手来源](https://www.aihero.dev/ai-coding-dictionary/primary-source)**（提交信息、PR、原始议题），这样它在两个意图之间做选择，而不是在两块文本之间做选择；只要两者相容，它就都保留。不相容时，它选符合这次合并既定目标的那一边，并说明付出的取舍。它不会为了掩盖冲突而编造新行为，也从不使用 `--abort`。它总是把合并推进到一个完成的提交。

## 什么时候用它

打 `/resolving-merge-conflicts`，或者在任务合适时由[代理（agent）](https://www.aihero.dev/ai-coding-dictionary/agent)自动取用。

当 git 已经卡在它自己解决不了的冲突上时用它。它只处理眼前这个冲突，不涉及冲突两侧之外的任何事：

| 你的处境 | 技能 |
| --- | --- |
| 正在合并或变基，工作树里有冲突标记 | 本技能 |
| 合并已完成，但某些东西开始以你看不出的原因出问题 | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |
| 想规划怎么切分工作，让分支少撞车 | 都不用：见下面关于并行工作的问答 |

## 一手来源优先于 `ours` 和 `theirs`

这个技能的存在，就是为了防止按开关解决冲突：`--ours`、`--theirs`，或者手工删掉看起来不那么重要的那块，让标记消失、构建能编译。这种解决方式语法上可以完美，却悄悄丢掉了某人有意做的改动。

你没读过的意图，你保不住。所以工作从历史（提交、PR、[工单（ticket）](https://www.aihero.dev/ai-coding-dictionary/ticket)）开始，然后才移到 diff。检查那一步也是同一个道理。技能会找到仓库自己的[自动检查](https://www.aihero.dev/ai-coding-dictionary/automated-check)，在提交之前跑一遍，因为合并是 git 里最容易产出“同时满足两个分支、却过不了任何一方测试”的代码的地方。

## 常见问题

**Claude Code 自己解决冲突已经挺好了。为什么还需要一个技能？**

增量价值在“找出一个手来源”和“跑反馈回路”这两步，否则你每次都得手工提示。没有提示的代理通常只凭 diff 给出一个看起来合理的解决方案，然后就停了。这个技能的价值在于它不让代理跳过的那两步：读清楚两边为什么存在，以及事后跑检查。相比一个优秀的[模型（model）](https://www.aihero.dev/ai-coding-dictionary/model)，收益不大，而且这是有意的。至少有一位读者预测，随着模型进步，这整个技能会变成空操作。

**我是不是该在并行代理之间把文件隔开，从源头上避免冲突？**

多数情况下不用。在并行任务之间把文件划开，成本大于收益，因为代理处理合并冲突已经够好，这个取舍没看上去那么苛刻。唯一值得保留的纪律是：大范围重构先做。一个大改名在十个分支从它分出去之后才合并，才是真正昂贵的场景。

一位用户关于并行工作树的报告提醒一点：当并行的[会话（session）](https://www.aihero.dev/ai-coding-dictionary/session)各自在自己的工作树里做一个工单时，合并回去最好由写这个改动的那个会话来干，因为只有它已经知道意图。如果最后让一个代理统一解决所有人的冲突，它就丢失了本技能第 2 步必须重建的那份[上下文（context）](https://www.aihero.dev/ai-coding-dictionary/context)。

**为什么绝不用 `--abort`？**

中止会把解决工作全部丢掉，下次再试还是同一个冲突，一点没变。这个技能是为“这次合并确实要发生”的情况写的。如果你已经决定它不该发生，那是调用之前要做的决定，而不是循环里的一个分支。

## 它在生效的表现

- 解决冲突时，代理会引用提交信息、PR 或议题，而不只是 diff 的 hunk。
- 每个 hunk 最后都保留双方的行为，或者有一条明确的说明，点出丢了什么、为什么。
- 结果里没有出现任何两边分支都没有的东西。
- 代理在提交*之前*就找到类型检查、测试和格式化并跑绿了，而不是等你发现哪里坏了之后。
- 结束时工作树是干净的、操作已完成；多提交的变基里，剩下的每个提交也都完成了。

## 它在哪里合用

一个随时可用的独立技能，不依赖任何其他技能：git 卡住时开始，树干净且已提交时结束。唯一真正的邻居是 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)，它在“合并干净完成、但合并后的代码行为不对”的那一点上接手：那是诊断问题，不是冲突问题。它在从想法到交付的主流程之外，所以前后该跑什么，看 [ask-matt](https://aihero.dev/skills-ask-matt) 那张图。
