## 它做什么

`wayfinder` 接手一项一次代理[会话（session）](https://www.aihero.dev/ai-coding-dictionary/session)装不下的工作。也就是那种你能说出**目的地**、却还看不见路线的想法。寻路把它画成议题跟踪器上一张共享的**地图**，由**决策工单**组成，然后逐个解决工单，直到路线清晰。

它做规划，不做构建。每张工单提出一个问题，答案是某个决定，不是某个构建切片。等有人真正动手之前不再剩下要决定的东西时，地图就完成了。这条规则把寻路工单和普通的实现[工单（ticket）](https://www.aihero.dev/ai-coding-dictionary/ticket)区分开，也是代理最常破坏的一条规则。地图变清晰后，寻路交出去，不继续进入代码。

## 什么时候用它

通过打 `/wayfinder` 调用；[代理（agent）](https://www.aihero.dev/ai-coding-dictionary/agent)不会自己去用它。

它是这套里最重的流程，所以触发条件很窄。这项工作必须大于一次代理会话能装下的量，而通往目的地的路线必须不清楚。分界是会话数：单会话规划用 `/grill-with-docs`，多会话规划用 `/wayfinder`。

| 你面前是什么 | 跑什么 |
| --- | --- |
| 一个界定清楚、一次坐下就能定下来的功能 | [grill-me](https://aihero.dev/skills-grill-me)，有代码库时用 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 一个全新项目，或者跨很多次会话的构建，路线还不清楚 | `/wayfinder` |
| 一条已经决定完的线程 | [to-spec](https://aihero.dev/skills-to-spec)：直接跳过地图 |
| 一张已经清晰的寻路地图 | [to-spec](https://aihero.dev/skills-to-spec)，然后 [to-tickets](https://aihero.dev/skills-to-tickets) 和 [implement](https://aihero.dev/skills-implement) |
| 一场已经长得太大的现有会话 | 说“交接给 `/wayfinder`”（[handoff](https://aihero.dev/skills-handoff) 既能桥接进地图，也能桥接出地图） |

全新项目不是必要条件。人们经常拿寻路用在遗留和半成品代码库上，在那里它可能更有用，因为很多迷雾是“这里已经成立的是什么”，而不是“我们该做什么”。

## 前提条件

地图和它的工单住在仓库的议题跟踪器上，所以寻路需要 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) 做好的跟踪器配置。那一步会写出一节“寻路操作”。那一节描述如何在 GitHub、GitLab 或本地 Markdown 上表达地图、它的子工单、阻塞关系和前沿查询。寻路通过你 `CLAUDE.md` / `AGENTS.md` 里的指针找到那份文档，而不是固定路径。没有配置跟踪器时，它退回本地 Markdown 文件。

跟踪器真的在干活。它的原生阻塞链接让前沿在跟踪器自己的界面里可见。在没有原生依赖链接的跟踪器上（比如自建的 Gitea），寻路从地图文字推断阻塞关系。那能用，但你得盯得紧一些。

## 地图、迷雾和前沿

**地图**是一条带 `wayfinder:map` 标签的议题，它的工单是它的子议题。它是**索引，不是仓库**。一个决定只存在一个地方，也就是它的工单，地图只给一行摘要和一个链接。会话以低分辨率加载地图，需要时再打开单张工单。这让地图能持续长大，而不必让每场会话都加载它全部的历史。

地图有四节：

- **目的地（Destination）。** 这张地图走完是什么样子。你先说出它，在任何工单存在之前，因为目的地固定了你衡量每张工单时用的范围。
- **目前的决定（Decisions so far）。** 每张已关闭工单一行，各带一个指向细节所在处的链接。
- **尚未说明（Not yet specified）。** 这就是**战争迷雾**：你能感到即将到来、却还说不锐利的决定。迷雾与工单的判据是*现在*能不能把问题说精确，不是能不能答出来。你解决一张工单，它前方的迷雾就清掉，你现在能说清的东西升级成新工单。
- **不在范围内（Out of scope）。** 目的地之外的工作。迷雾只*朝着*目的地聚集，所以在范围之外的工作一直关着，永不升级。

**前沿**是未关闭、未阻塞、未被领取的工单集合（已知世界的边缘）。会话在动手之前把工单指派给自己，从而领取它。被指派人*就是*领取，所以并发会话会跳过那张工单。会话用工单的名字指代它，绝不用光秃秃的 `#42`，因为一墙议题编号在叙述里很难读。

## 四种决策工单

每张工单带一个 `wayfinder:<type>` 标签。每张工单要么是 **[HITL](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)**（和一个自己会说话的人一起做），要么是 **[AFK](https://www.aihero.dev/ai-coding-dictionary/afk)**（代理独自驱动）。HITL 工单只通过那场现场交流解决。一个自己回答自己的[拷问（grilling）](https://www.aihero.dev/ai-coding-dictionary/grilling)问题的代理，已经破坏了它。

| 类型 | 模式 | 什么时候用 | 由谁解决 |
| --- | --- | --- | --- |
| `grilling` | HITL | 默认。这个问题靠聊能定下来。 | 在新会话里跑 [grilling](https://aihero.dev/skills-grilling) 加 [domain-modeling](https://aihero.dev/skills-domain-modeling) |
| `prototype` | HITL | “这该长什么样”或“它该怎么表现”：说话定不下来的问题。 | [prototype](https://aihero.dev/skills-prototype)，并从工单链接到建出来的产物 |
| `research` | AFK | 工作目录之外的一个事实挡住了某个决定。 | 一个 [research](https://aihero.dev/skills-research) [子代理（subagent）](https://www.aihero.dev/ai-coding-dictionary/subagent)，在画地图时启动，在 `research/<name>` 分支上并行运行 |
| `task` | 两者皆可 | 没什么可决定，但手工工作挡住了某个决定，比如开通访问权限、注册服务，或者搬运数据以便看清它的形态。 | 代理能独自做的就独自做，否则给一份精确的人工清单 |

`task` 是唯一动手*做*而不是决定的类型。它只因为解除某个决定的阻塞才留在地图上，绝不因为它交付目的地的一部分。这个类型在实践中最容易出问题。代理把它读成实现步骤，开始在地图里写产品代码。

研究是“每会话一张工单”的唯一例外。

## 常见问题

**这和 `/grill-with-docs` 有什么不同？我该从哪个开始？**
看会话数，不看项目大小。`/grill-with-docs` 是单会话规划；寻路是多会话规划。如果你能在一场对话里握住整件事，拷问更便宜也更好，而寻路在那种情况下更慢更密。社区的简略说法是：只有工作装不进一次会话时，寻路才说得通。这是关于寻路被问得最多的问题。人们一直问，是因为技能描述不告诉你自己的任务落在那条线的哪一边。会话数得你自己判断。

**它问“目的地”时，指的是这场会话的结尾，还是所有事情的结尾？**
整张地图的结尾，不只是第一场会话。这个问题读起来有歧义，但寻路按定义就是多会话工具，所以限定在一场会话的答案从来讲不通。典型的目的地是一份要交出去的[规格说明（spec）](https://www.aihero.dev/ai-coding-dictionary/spec)、一个规划开始前要定下的决定、一个概念验证，或者一次原地改动，比如数据迁移。

**地图清了。寻路不是已经写好规格说明、做好工单了吗？为什么还需要 `/to-spec` 和 `/to-tickets`？**
不是。寻路的工单是决策工单，地图关闭时它们也都关闭了。剩下的是满满一张互相链接的决定的地图，那不是构建计划。[to-spec](https://aihero.dev/skills-to-spec) 把这些链接起来的决定收拢成一份规格说明（`/to-spec #<map_issue>`），[to-tickets](https://aihero.dev/skills-to-tickets) 再把那份规格说明切成曳光弹实现工单。如果你把地图直接接进 [implement](https://aihero.dev/skills-implement)，就跳过了这次收拢，丢掉链接起来的细节。只有当这项工作最终确实不大时，才直接去实现。有人跑这条更短的流水线，报告说也能用。多出来那两步给你一份审查者或同事能读的明确规格说明，这在你不独自工作时更要紧。

**我的代理在寻路会话中途开始写生产代码。**
这是关于这个技能被报告最多的失败，而技能里一个真实的缺口造成了它。你可以在地图的 **Notes** 里覆盖寻路“只规划，不动手”的默认。但 Notes 是代理写的，于是这条约束和它的豁免都住在一个被约束的代理自己拥有的文件里。一位用户看着代理把“这张地图承载执行”写进自己的 Notes。后来的会话里，代理把那行读成许可，在一个在线服务器上动手建。技能对“我是说用默认”没有硬性停止。在它有之前，凡不是你自己画的地图，先读 Notes，把实现放在别的会话里，并把任何看起来像构建切片的 `wayfinder:task` 当成标错了类型。

**我画了 27 张工单，等我做到第 13 张，剩下的就不成立了。**
这个问题逐字来自一份用户报告，其他人也报告了同样的结果。默认情况下，寻路做全面规划。当后面的工单建立在被前面的工单推翻的假设上时，地图就掉进批评者指责这个技能的那类瀑布陷阱。两件事有帮助。第一，把地图限定在一个有边界的目的地上，而不是整个产品。用户报告说限定在一个定义清楚的 epic 上的地图，表现比一张铺开的“实现 V1”好。目标是交付小增量，不是规划一件很大的事。第二，积极地做[原型（prototype）](https://www.aihero.dev/ai-coding-dictionary/prototyping)。路线之所以能保持最新，是因为便宜而具体的产物在实现依赖它之前就暴露了不确定性。寻路是“原型最大化”，不是“规划最大化”。

**我能并行做几张工单吗？**
前沿让你看到哪些工单可以拿，而阻塞关系在纸面上让并行工作安全。实践中，一次一张工单是更安全的默认。如果你同时做两张拷问工单，一个会话可能问你一个你刚在另一个会话里答过的问题，因为这些会话不共享[上下文（context）](https://www.aihero.dev/ai-coding-dictionary/context)。原型工单也有一个已知缺口。一位用户报告代理建了三个界面版本、自己挑了一个、把工单关了。那个选择是你的，而技能目前说得还不够清楚。如果你确实并行跑工单，先自己审一遍依赖图。

**我必须用 GitHub Issues 吗？**
不用。任何议题跟踪器都行。GitHub 的支持最好，因为它的原生子议题和阻塞关系让前沿不用打开地图就可见。人们也用 GitLab、Linear、Jira 和本地 Markdown。有两点提醒。在没有原生阻塞的跟踪器上，寻路从文字推断依赖图，你必须手工纠正。本地 Markdown 把产物放进你的仓库，这不推荐，因为存在仓库里的材料容易意外地久留下来。开源维护者遇到的是相反的问题（公开跟踪器被代理生成的规划工单塞满），常常还是选本地 Markdown。

**拷问太累人。每个问题都三段长。**
这是关于寻路最尖锐的未解决抱怨，目前没人修。一位用户这样拆解：啰嗦本身就造成决定疲劳，而长度掩盖了代理*为什么*问这个问题，于是地图长大后你就丢失了从决定到决定的链条。啰嗦看起来是当前这批[模型（model）](https://www.aihero.dev/ai-coding-dictionary/model)的属性，而不是这个技能的。用户试过两种缓解：降低[推理投入（reasoning effort）](https://www.aihero.dev/ai-coding-dictionary/effort)，以及在你全局的 `CLAUDE.md` 里加一条平实的指令。不管怎样都要预期在这里好好动脑。寻路要求你大量思考，而这正是它大部分的意义，不是缺陷。

**我已经关掉的一个决定被证明是错的。我改旧工单还是开新的？**
没有官方指引，而代理的默认做法帮不上忙。它倾向于绕开那个坏决定去设计，而不是去挑战它，所以你得自己掌舵。有效的做法是明确告诉寻路变了什么。它会更新地图、修订受影响的工单，并在已关闭的工单上留言。你能从地图中途的范围变化里恢复。但如果你*设计*一张地图去变，那就是范围不对的信号。

**`decision-mapping` 去哪了？**
就是这个技能。v1.1 把它改名为 `wayfinder`，用 `/wayfinder` 调用。“决策地图”是行话，也不准确，因为四种工单类型里只有一种本身是个决定。新名字给技能一套前后一致的词汇（目的地、战争迷雾、前沿、地图），而不是在它之上再造一个词。这个单元保留了“决策”这个词：寻路工单是**决策工单**，免得人们把它读成实现工单。

## 它在生效的表现

- 目的地写在纸上、达成一致之后，才出现第一张工单。
- 每张未关闭的工单读起来像一个问题。任何读起来像“构建 X”的工单，要么标错了类型，要么属于地图的下游。
- 你不用打开地图就能在跟踪器上看到哪些工单可以拿，因为原生阻塞显示了前沿。
- 一次会话解决一张工单，把答案作为解决评论发布，关闭它，并往地图的*目前的决定*里加一行。然后它停。
- **尚未说明**随着时间变小。迷雾升级成工单时，它离开那一节，不会两处都出现。
- 开场那次广度优先的拷问完全没摸出迷雾时，技能停下来，告诉你这项工作小到可以跳过地图。
- 跑完地图的那场会话把你指向规格说明，而不是一个拉取请求。

## 它在哪里合用

`wayfinder` 是一个**视情况而定的入口**，不是默认起点。多数工作仍然从拷问引领的“想法 → 交付”链开始。当想法大到一次会话握不住时，你用寻路。它在 [to-spec](https://aihero.dev/skills-to-spec) 处重新汇入那条链，因为清晰的地图是交出去的，不继续构建。

大部分工作发生在寻路所排期的其他技能里。[grilling](https://aihero.dev/skills-grilling) 和 [domain-modeling](https://aihero.dev/skills-domain-modeling) 解决默认的工单类型，[prototype](https://aihero.dev/skills-prototype) 解决说话定不下来的工单，[research](https://aihero.dev/skills-research) 作为子代理运行，让它的阅读留在你的会话之外。[handoff](https://aihero.dev/skills-handoff) 把工作移进移出：从一场长得太大的对话移进地图，以及在会话中途出现支线任务时移出地图。其他情况，[ask-matt](https://aihero.dev/skills-ask-matt) 会带你在整套技能上导航。
