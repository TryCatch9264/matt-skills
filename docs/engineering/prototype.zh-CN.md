## 它做什么

`prototype` 写**用来回答某个问题的一次性代码**：这个状态模型感觉对吗，或者这个界面该长什么样。问题在先，它决定你建什么。答错问题的原型，做得再漂亮也是浪费。

一次性是关于代码*怎么写*的约束，不是要销毁它的承诺。没有测试，除了让它跑起来必需的之外没有错误处理，没有抽象，没有持久化，因为这些都无助于你学那唯一要学的东西。有两样东西留下来。答案并进真实代码，原型进 main 之外的一条分支，作为答案的证据。

## 什么时候用它

打 `/prototype`，或者在任务合适时由[代理（agent）](https://www.aihero.dev/ai-coding-dictionary/agent)自动取用。

撞上一个靠说话解决不了的问题时立刻用它：一个边界情况在脑子里装不下的状态机，一个不并排看到三个版本就想不出来的界面。[拷问（grilling）](https://www.aihero.dev/ai-coding-dictionary/grilling)会话遇上这类问题会变得很长。代理不停改写，你不停猜，范围随之膨胀。停止拷问，做出那个一次性版本，看一眼，然后用一句话回答。如果反过来是已经建好的东西行为不对、你想知道为什么，用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)：原型探索的是建什么，不是已建的东西为什么坏。

你有时也会在没主动选择的情况下来到这里。[wayfinder](https://aihero.dev/skills-wayfinder) 会在它的地图上开 `prototype` 类型的决策[工单（ticket）](https://www.aihero.dev/ai-coding-dictionary/ticket)，你就用这个技能处理其中一张。

## 两条分支

问题挑分支，两条分支产出的东西不同：

- **“这套逻辑／状态模型感觉对吗？”**：一个**可分享的单个 HTML 文件**。一个自包含的页面，不用构建、不用服务器，双击就能打开。它带一个带标签的状态面板，每次点击后重新渲染；带自由操作的按钮，可以按任意顺序摆弄模型；还带分标签页的**引导式演练**（一个标签页一个场景，每个下面是为该场景准备的有序按钮）。所有标签都用领域语言，所以你可以把它交给设计师、产品经理或领域专家，让他们自己试这个模型。页面背后的逻辑是一个小的纯模块（一个 reducer、一个状态机、一组函数），里面没有 DOM 代码，这样你能把验证过的版本直接搬进真实代码。
- **“这个应该长什么样？”**：同一个路由上几个**截然不同**的界面版本，通过底部浮动条和 `?variant=` URL 参数切换。版本之间必须在结构上有分歧，而不是颜色；三张稍作调整的卡片网格什么都回答不了。它们尽可能渲染在真实页面里，面对真实数据和真实密度，因为在空页面上评判的版本总是看起来不错。

两条分支都把状态放在内存里，都不需要准备就能启动，都在每步之后给你看完整状态。当你发现自己开始给它加固（加测试、接真实数据库、为某个以后可能会要的情形做通用化），你就已经不在做原型了。

## 原型是一手来源

做完的原型留下两样东西，它们去不同的地方。

你把**答案**（结论，以及它解决的是哪个问题）记到某个长期的地方：提交信息、ADR、实现议题。main 保留答案，以真实代码的形式。

**原型**是答案所出自的可运行证据，你不要删掉它。它也不属于 main，因为没人维护它，它会很快过时。所以你把它提交到 main 之外的一条一次性 `prototype/<name>` 分支上，永不合并，并在实现议题上留下指向那条分支的[上下文指针（context pointer）](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。main 保持干净，下一个接手这项工作的人也能找到并重新跑起这个原型。

## 常见问题

**等等，原型不是应该删掉吗？**
现在不是了。以前是：做出来、留下答案、把代码丢掉。对那种做法最强的反对不在速度上，而在于*下一个[会话（session）](https://www.aihero.dev/ai-coding-dictionary/session)接手这项工作的人，手里有什么可用？* 一份原型的文字摘要会失掉让它有说服力的那个东西。所以技能现在把原型当[一手来源（primary source）](https://www.aihero.dev/ai-coding-dictionary/primary-source)。它落在 main 之外的一条 `prototype/<name>` 分支上，实现议题指向它。变的是代码住在哪里，不是纪律；它仍然永不合并进 main。

**它以前是做一个终端应用。那个去哪了？**
逻辑分支现在改为产出一个可分享的单个 HTML 文件。终端应用只有克隆了仓库、装好了运行时的人才能操作，这恰好排除了原型最需要其意见的那些人：设计师、产品经理、知道这个状态模型该是什么意思的领域专家。一个自包含、双击就能打开、通过邮件发来发去还能用的文件，任何人都能操作。底下那个纯逻辑模块没变，仍是你要搬进真实代码的那部分。

**代理让我 `/prototype`，而我本该在实现。**
这是一个已知的命名问题。不了解流程的代理，一看到工单存在，就把 `prototype` 这个通用又有吸引力的词读成“显而易见的下一步”。所以即使设计在对话里已经定了，代理也会按名字推荐它。如果你已经知道要建什么，下一步是按工单跑 `/implement`。只有当某个具体的设计问题还没解决、说话又解决不了时，才去做原型。

**我该不该在构建任何生产功能之前先把整个应用原型化（比如为了给潜在客户演示）？**
那是另一个东西，只是碰巧和这个技能同名。这里的原型限定在一个问题上，而“整个应用是什么”不是一个问题。全应用原型没有自然的停止点，于是它会滑成生产应用：清理那一遍永远不会发生，而在原型规则下写的代码（没测试、没错误处理）最后落到了用户面前。如果你需要销售演示，就明确地把它当演示来建，并说清没有一部分是生产代码。如果要解决一个设计问题，就把它砍到那个问题上。

**我该怎么在它自己的会话里跑它？**
原型住在自己的目录里，会产生大量你不想留在提出问题的线程里的[上下文（context）](https://www.aihero.dev/ai-coding-dictionary/context)，所以在别的地方跑，只把答案带回来。用 [handoff](https://aihero.dev/skills-handoff) 把工作移进那个会话，再把答案带回来。

**这不就是烧词元最快的方式吗？**
有可能，如果原型化的是本来靠说话就能回答的问题，或者让一个原型蔓延到整个功能上。值得做的比较不是词元对零，而是[词元（token）](https://www.aihero.dev/ai-coding-dictionary/token)对“建错了状态模型、等它有了生产调用方才发现”。把问题保持窄、把运行保持短，花费就还是成比例的。

## 它在生效的表现

- 你能用一句话说出这个原型存在的目的是回答哪个问题，而且它写在演示的最上面，不只是在你脑子里。
- 不读代码的人也能操作逻辑演示。他们打开文件，在演练标签页里按按钮，用自己的话描述看到了什么。
- 有人说“等等，这不该可能”或者“嗯，我以为 X”。那是*想法*本身的缺陷，而原型正是为了这个。
- 界面版本之间在布局和信息层级上有分歧，不只是颜色和文案，而你收到的反馈是“B 的页头配 C 的侧栏”。
- 一次坐下来就答完了。如果一天后你还在建它，问题太大了；拆开。
- 结束的时候，main 里只有决定、没有原型的任何部分，而实现议题指向那条仍然保留它的分支。

## 它在哪里合用

`prototype` 是一个**随时可用的独立技能**：你用它解决一个设计问题，然后回到自己的工作。另有技能也会跑它。

最常跑它的是 [wayfinder](https://aihero.dev/skills-wayfinder)。一张 wayfinder 地图由**决策工单**组成，而 `prototype` 是工单可取的四种类型之一：用在挡住前路的问题正是“这个该长什么样”或“它该怎么表现”、而且讨论解决不了的时候。讨论含糊时，wayfinder 造一个具体的东西来反应，这个技能就造那个东西。答案解决掉一张原型工单，地图把原型作为资产链接过去。

其他邻居在那的上下游。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 处理可拷问的问题；不可拷问的转到这里，而那句一行的答案回到访谈里去。下游，验证过的状态模型或界面方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的既定输入，后者可以把原型产出的、承载决定的片段内联进来，而不必用文字描述它。其他情况，[ask-matt](https://aihero.dev/skills-ask-matt) 会带你在整套技能上导航。
