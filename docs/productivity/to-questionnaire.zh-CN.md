## 它做什么

`to-questionnaire` 把一个你自己定不下来的决定变成一份**问卷**：一份 Markdown 文档，交到唯一掌握你缺的那部分信息的人手上，让他异步填写，或者你们两人在会上一起走一遍。

它只就**发送**这件事拷问你，绝不碰主题。就主题做访谈没有意义，因为不熟悉主题正是你要写信给别人的原因。所以它问的是你总能答上的两件事（这份东西发给谁、你需要从他那里拿回什么），并把文档里的每个问题都对准这两者之间的**差距**。

## 什么时候用它

通过打 `/to-questionnaire` 调用；[代理（agent）](https://www.aihero.dev/ai-coding-dictionary/agent)不会自己去用它。

当一个决定被卡在别人脑子里的知识上时用它：客户、领域专家、掌握业务规则的高管、你不在同一张桌子上的同事。要哪个技能取决于答案在哪里：

| 答案在…… | 用 |
| --- | --- |
| 你自己脑子里，只是还没磨清 | [grill-me](https://aihero.dev/skills-grill-me) |
| 代码库里 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人脑子里 | `to-questionnaire` |
| 谁的脑子里都还没有，这个问题需要有东西可以对着反应 | [prototype](https://aihero.dev/skills-prototype) |

常见情形是一场[拷问（grilling）](https://www.aihero.dev/ai-coding-dictionary/grilling)会话卡住了，因为其中有些问题不该由你回答。在同一场对话里跑 `/to-questionnaire`，把那些问题带出去问，然后把答案带回来继续。

## 发送，而不是主题

访谈只有两轮，然后就结束。

- **发给谁？** 他们的角色、专长、和你的关系。这决定语气，也决定文档得承载多少背景。外部客户需要交代情况；同事不需要。
- **你需要拿回什么？** 你一个人定不了的具体决定或事实。这会变成成品文档的清单。你点到的每一项都配一个对准它的问题。

之后全是起草。技能把文件写到当前目录的 `to-questionnaire-<slug>.md`。不用准备，没有工作区，也没什么要配置。

## 文档

文档是一份**发现问卷**，因为你缺背景、收件人有背景。这决定了它的形状：

- 一行目的，点出依赖它的那个决定；再加一小段背景，给一个完全不了解你处境的收件人。
- 问题按**最重要在前**排序，按主题标题分组，因为异步填写可能只给一次机会。
- 一个问题只讲一件事，绝不复合提问，下面配一个回答占位；只有当问题可能被误读时，才加一句*为什么这很重要*。
- 明确允许回答“我不知道”，因为标出来的不确定有用，而一个读起来像事实的自信猜测没有。
- 收尾的兜底问题：有什么我们没问到但应该知道的？

文档有意不是两样东西。它不是**分支式**的：问题是一份平铺、分组的清单，不是一棵“答了 A 就跳过 D 节”的树。它也不是**多收件人**的：一次运行产出一份文档，给一个人。

## 常见问题

**它会读我的拷问会话，从中提取问题吗？**
不作为单独一步。这个技能没有读取阶段。它问发送的事，然后起草。它能在一场拷问会话之后接着有用，是因为你在**同一场对话**里运行它，所以那场[会话](https://www.aihero.dev/ai-coding-dictionary/session)已经在[上下文（context）](https://www.aihero.dev/ai-coding-dictionary/context)里，起草时能用上。如果你在新会话里启动它，它对拷问一无所知，你回答“你需要拿回什么？”时得自己再交代一遍主题。

**缺的答案不在同一个人那里。它能按收件人拆开吗？**
不能。第一步问的是*那个*收件人，单数，整个文档的语气和背景都对着他调。如果三个人各持答案的一部分，就跑三次，一人一次。有人要求过一份按专业或角色分流问题的文档，但没有发布。

**问题是相互依赖的吗：它会根据前面的答案跳过某些小节吗？**
不会。依赖式问题的设计探索过，但没有发布。产出是一份静态文档：按主题分组、最重要在前、每个问题都有效。反对意见也有道理：一个在拿到真实答案之前就要往后规划两三个问题的[模型（model）](https://www.aihero.dev/ai-coding-dictionary/model)规划得很差，而分支式文档必须在每个答案之前把全部问题都规划好。

**如果收件人也不知道呢？**
文档会让他们说出来。它明确要求“我不知道”和部分回答。标出来的不确定比猜测值钱，因为一个含糊的回答和一个自信的错答，回到你上下文里之后看起来一模一样。

**它会把它发到什么地方吗（Slack、议题跟踪器、邮件）？**
不会。它在当前目录写一个 Markdown 文件，并告诉你路径。发送是你的事：粘进[工单（ticket）](https://www.aihero.dev/ai-coding-dictionary/ticket)、丢进 Slack 线程、作为附件发邮件，或者投在共享屏幕上当场一起填。这四种都有人手工做过。

**这不就是批处理模式的 `/grill-me` 吗？**
不是。`grill-me` 本来就是按**轮**提问的。它一次问出全部开放问题的前沿，然后根据你的回答重算，所以它已经满足了“一次给我所有问题”的需求。`to-questionnaire` 的差别在另一条轴上：它关乎答案在谁脑子里，而不是问题怎么送达。想更快地自己回答，用 `grill-me`。想从别人那里取出来，用这个。

**我不用技能，直接让代理做不行吗？**
行，而且在这个技能出现之前很多人都这么做过：`OPEN_QUESTIONS.md` 文件、发给客户的表格、每个没答的问题开一张“需要更多信息”的工单。技能给你两样东西：访谈不会偏到主题上去，以及产出的文档形态能让不懂技术的收件人填得下去。如果你已经有自己惯用又有效的格式，就不需要这个。

## 它在生效的表现

- 它问收件人是谁、你需要拿回什么，然后就不问了。如果它开始问主题本身，技能就走偏了。
- 你列出的每一项“我需要拿回什么”，都能在文件里追溯到一个问题。
- 问题读起来是对着*收件人*知道的东西提的，而不是把你自己的开放问题原样抄下来。
- 你可以把文件交给一个不在场的人，他会知道自己为什么会收到它、什么时候之前要回。
- 带回来的答案能用于下一轮拷问，而不是又变成一堆新问题。

## 它在哪里合用

`to-questionnaire` 是一个随时可用的独立技能。你在自己的知识到头、下一步是去问别人而不是再跑一个技能的地方用它。最常见的是流程中途，规划卡在一件不该由你决定的事上。

它的邻居是 [grill-me](https://aihero.dev/skills-grill-me)，两者的差别在于答案住在哪。拷问从你这里取答案；问卷从别人那里取。把带回来的东西喂进下一轮拷问，或者如果这项工作要走向构建，就喂给 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。不确定当下该用哪个技能时，[ask-matt](https://aihero.dev/skills-ask-matt) 会帮你导航。
