# 问 Matt

你记不住每个技能，所以问一下。

在说明某个技能做什么、或者建议跳过某一步之前，先读那个技能的 SKILL.md：这里的摘要只用于大致定位。

**流程**是穿过技能的一条路径。多数路径沿一条**主流程**走，两条**入口**汇入它。其余都是独立技能，或者跑在下面的一层词汇。

## 主流程：想法 → 交付

多数工作走的路线。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 通过访谈把想法磨利。只要你**在有工作目录的情况下工作**，就从这里开始：它是有状态的，会把学到的东西留在 `GLOSSARY.md` 和 ADR 里。（没有工作目录？改用 `/grill-me`，见“独立技能”一节。两者跑的是同一个 `/grilling` 内核；`grill-with-docs` 是留下一份文字记录的那个，所以只要身边有仓库可以留，它就是两者中更好的选择。）
2. **分岔：所有问题都能在对话里定下来吗？** 如果某个问题需要一个能跑起来的答案（状态、业务逻辑、必须亲眼看的界面），就绕道走原型，两个方向都用 **`/handoff`** 搭桥（原型住在自己的目录里，这正是 `/handoff` 的用途；见“阶段边界”）：
   - 先 **`/handoff`** 出去，然后对着那个文件开一个新会话，
   - 用 **`/prototype`** 以一次性代码回答这个问题，
   - 把学到的东西 **`/handoff`** 回来，并从原来那条想法线索里引用它。
3. **分岔：这是要跨多次会话的构建吗？**
   - **是** → 先 **`/to-spec`**（把线索整理成规格说明），再用 **`/to-tickets`** 拆成曳光弹工单，每个工单声明自己的**阻塞关系**。然后按两种方式之一推进工单：
     - 每个工单跑一次 **`/implement`**，**每个之间 `/clear` 一次上下文**。在本地跟踪器上，那是 `.scratch/<feature>/issues/` 下一个工单一个文件，手工按阻塞顺序推进；在真实跟踪器上，阻塞关系变成原生阻塞链接，所以任何阻塞项已完成的工单都能被拿起来。每个工单都自足，所以上一个的上下文可以丢掉。
     - 用 **`/implement-spec`** 一次跑完整份规格说明。它把工单当作**任务图**来读，沿可领取的**前沿**并行运行实现子代理，并把所有东西落到一个**集成分支**上。当你更想统筹整个构建、而不是自己逐个驱动工单时用它。
   - **否** → 就在这里 **`/implement`**，在同一个上下文窗口里。

   无论哪种方式，代码都是靠驱动 **`/tdd`**（一次一个红-绿切片）构建出来的，并用 **`/code-review`** 收尾，也就是对 diff 的双轴审查（标准 + 规格）。`/implement` 每个工单都跑这两样；`/implement-spec` 的实现子代理各自驱动 `/tdd`，最后由它对集成分支跑一次 `/code-review`。只想要先写测试把某个具体行为建出来、不需要完整规格说明时，单独用 **`/tdd`**；想对照某个固定点审查一个分支或 PR 时，单独用 **`/code-review`**。

   工作作为拉取请求提交上去时，**`/pr`** 决定正文的形态：能展示改动的最小视图、说明改动有效的改前／改后证据，以及单向门还是双向门的判断。它是模型调用的，所以代理每次写 PR 都会去用它。

4. **`/retro`** 收束循环。一次构建之后，尤其是走偏了的那次，它回看这次会话，就代理的**环境**（而不是代码）提出改动建议：导航指针、自动检查、`/code-review` 执行的编码规范、引导文件、工具。机械性的错误变成确定性检查；判断类问题变成编码规范。下一次构建于是从更好的环境开始。

### 上下文整洁

把第 1 到 3 步保持在**一个不间断的上下文窗口**里（`/to-tickets` 之前不要压缩或清空），让拷问、规格说明和工单都建立在同一套思考上。之后每个 `/implement` 都从工单出发、全新开始。`/retro` 在它回看的那次会话里跑，趁还没清空；清空之后，就把它指向那次会话的日志。

这里的限制是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能锐利推理的窗口（在顶尖模型上约 150k token）。如果一次会话在 `/to-tickets` 之前就接近它，不要硬撑着让质量下降；在最接近的阶段边界处 `/compact` 再继续（见“阶段边界”）。

## 入口

一种会产生工作的起始处境，之后汇入主流程。

- **缺陷和需求堆积起来** → **`/triage`**。它让议题沿分诊角色流转，产出代理可以直接开工的议题，之后由 **`/implement`** 接手。

  分诊只用于**不是你创建的**议题：缺陷报告、外来的功能需求、任何原始抵达的东西。`/to-tickets` 产出的工单已经是代理可开工的，所以**不要去分诊它们**。

- **有东西坏了** → **`/diagnosing-bugs`**。针对难缠的那些：一眼看不穿的缺陷、时有时无的间歇故障、在两个已知良好状态之间潜入的退化。在拿到**紧的反馈回路**（一条已经能对*这个*缺陷变红的命令）之前，它拒绝做理论推演，然后用回归测试修复。修复到位后，在同一次会话里跑 **`/retro`**，问是什么本该防住这个缺陷；如果真正的发现是没有合适的接缝把它固定住，那就是 **`/improve-codebase-architecture`** 的活。

- **一项庞大而模糊的工作：全新项目或巨型功能构建，大到一次会话装不下** → **`/wayfinder`**，这里认知要求最高的一条流程。当从这里到目的地的路还看不见时，它在议题跟踪器上画出一张**共享地图**，由**决策工单**组成，逐个解决，产出**决定，而不是交付物**，直到迷雾被推后、路清晰起来。**`/grill-with-docs`** 是把一次会话就能握住的想法磨利，寻路则是针对你握不住的那个想法；它更慢、更密，所以只留给这种情形，绝不用于范围清楚的功能。

  地图变清晰后，**它交出去，自己不构建**：在 **`/to-spec`** 处汇入主流程，那里把地图上互相链接的决定收拢成一份可执行的计划，之后照常 `/to-tickets` 和 `/implement`。把地图直接接进 `/implement` 会跳过这次收拢，把链接起来的细节丢掉；所以只有当这项工作最终确实不大时，才直接去 `/implement`。

## 代码库健康

不是功能工作，只是维护。

- **`/improve-codebase-architecture`** 在你有点空闲、想让代码库对代理更好用时跑。它把**加深机会**摆出来；挑中一个就*产生一个想法*，你可以带进主流程的 `/grill-with-docs`。它是找出候选的勘察；**`/codebase-design`**（下面）是设计选中那一项的案台。

## 底下的词汇

两个模型调用的参考，跑在其他技能*下面*，各自是自己那套词汇的唯一出处。当出问题的是**词**而不是过程时，直接用它们；或者让上面的技能把它们拉进来。

- **`/domain-modeling`**：磨利项目的*领域*语言：质疑含糊的用词、拆解一个含义过多的词（一个“account”干三份活）、把难以撤销的决定记成 ADR。它是 `/grill-with-docs` 驱动的那套主动功课，用来让 `GLOSSARY.md` 保持为一份干净的术语表。
- **`/codebase-design`** 是设计模块*形状*的深模块词汇（模块、接口、深度、接缝、适配器、杠杆、局部性）：在干净的接缝处把大量行为放在小接口后面。`/tdd` 和 `/improve-codebase-architecture` 都用这套话。

## 阶段边界

**阶段**是会话里的一个工作块：拷问、实现、QA。在两个阶段之间的**边界**上，你有五个选项，而从中挑选是整张图里最模糊的决定：

- **继续**：留在原地。不花代价，不丢东西。
- **`/clear`**：清空窗口，适用于这里的一切对接下来都不重要时。
- **`/handoff`** 写一份可移走的 Markdown 文件。适用范围很窄：只用于**新的 harness**、**新目录**、**同事**，或者**在阶段中途**分出支线任务。它换来的是可携性。
- **子代理**：把一件界定紧凑的任务送到它自己的窗口，拿回一份报告。
- **`/compact`** 压缩当前上下文并用它种出一个新会话。它是**默认选项**，排在树的底部而不是第一选择。

有序的判断树见 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.zh-CN.md)：五个问题、每个分支背后的理由，以及为什么一手来源的代价让**继续**成为首先要排除的那个。要在边界处做决定；阶段中途，要么继续，要么把剩下的拆给子代理。

## 独立技能

完全在主流程之外。

- **`/grill-me`**：和 `/grill-with-docs` 一样不留情面的访谈，但**无状态**：不在本地保存任何东西，也不建 `GLOSSARY.md`。当你**不在工作目录里工作**时用它（磨利一份计划、一个设计、一篇文字，任何底下没有仓库的东西）。如果你在工作目录里，就改用 `/grill-with-docs`：它跑同一场访谈，还留下一份文字记录，所以严格来说它更好。
- **`/grilling`** 是访谈内核本身：一轮一轮来、盯住前沿、事实是代理的活而决定是你的。`/grill-me` 和 `/grill-with-docs` 是两条有名字的入口，`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 内部也都会跑它。只有当你想要不带任何包装的访谈时才直接用。
- **`/prototype`** 是回答一个设计问题的小型一次性程序：这个状态模型感觉对吗，或者这个界面该长什么样。一次性是关于代码怎么写的约束，不是要销毁它的承诺：答案并进真实代码，而原型本身作为**一手来源**保留在 main 之外的一条 `prototype/<name>` 分支上，从实现议题指过去。它是主流程第 2 步的那次绕道，但任何在纸上难以解决的设计问题都可以随时用它。
- **`/research`**：把读材料的苦活交给**后台代理**：它针对**一手来源**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它读的时候你可以继续干活。它产出的文件是要*带进*主流程 `/grill-with-docs` 的东西，因为研究是喂给思考的，不是替代思考。
- **`/to-questionnaire`** 用在你被挡住的原因既不在你脑子里、也不在代码库里，而在**别人**脑子里的时候，它会写一份问卷让对方填。它是 `/grill-me` 的反面：不是就主题访谈你，而是就**发送**这件事访谈你（发给谁、需要拿回什么），并把问题对准那个差距。带回来的材料可以喂给 `/grill-with-docs` 或 `/to-spec`。
- **`/wizard`** 用于只有**人**能做的步骤：配置基础设施、设置凭据或 CI 密钥、在不熟悉的第三方后台里点来点去、跑一次性迁移或切换。它生成一个交互式 bash 脚本，打开每个网址、收集每个值，写进 `.env` 和 GitHub 密钥，于是这套流程不再是每次都要向代理重新解释的东西。它是模型调用的，所以代理一撞上只有你能过的墙就会去用它。代理自己能做的就该自己做；这个用于人确实在环路里的情形。
- **`/wait-what`** 是对一条没被听懂的消息的纠偏。在对话中途、在任何其他技能里用它，代理会用你缺的上下文、用平实的语言、用 `GLOSSARY.md` 的词汇，把它刚说的话重新讲一遍。它是事后补救；`/grill-with-docs` 是事前的解决办法，因为早点约定共同语言才是让行话从一开始就不出现的方法。
- **`/teach`**：跨多次会话学一个概念，把当前目录当作有状态的工作区。
- **`/writing-for-agents`** 是写代理阅读的文档的参考：技能、AGENTS.md、被指向的文档。

## 前置条件
