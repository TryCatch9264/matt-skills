对 `HEAD` 与用户给出的固定点之间的 diff 做双轴审查：

- **标准**：代码是否符合本仓库写明的编码规范？
- **规格**：代码是否忠实实现了它来源的议题／规格说明？

两条轴都作为**并行子代理**运行，免得互相污染上下文，本技能再把它们的发现汇总起来。每个子代理都使用全新的上下文窗口启动。

议题跟踪器应当已经提供给你。如果没有，让用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定比较基准

用户说什么是固定点，它就是固定点（提交 SHA、分支名、标签、`main`、`HEAD~5` 等）。如果他们没说，就问。

把 diff 命令确定下来一次：`git diff <fixed-point>...HEAD`（三点，这样比较的是 merge-base）。再用 `git log <fixed-point>..HEAD --oneline` 记下提交清单。

继续之前，先确认固定点能解析（`git rev-parse <fixed-point>`）且 diff 不为空。错误的引用或空 diff 应当在这里失败，而不是在两个并行子代理里面失败。

### 2. 确定规格说明的来源

按下面的顺序找来源规格说明：

1. 提交信息里的议题引用（`#123`、`Closes #45`、GitLab 的 `!67` 等），按跟踪器文档里的流程取回。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能相符的规格说明文件。
4. 什么都没找到，就问用户规格说明在哪里。如果他们说没有，**规格**子代理会跳过并汇报“没有可用的规格说明”。

### 3. 确定规范的来源

在仓库里搜索每一个说明代码应当怎么写的文件。`CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 存在时，必须在清单里。

除了仓库自己写明的东西，标准轴始终带着下面这份**坏味道基线**：一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没写也适用。有两条规则约束它：

- **仓库优先。** 仓库写明的规范总是胜出；如果它认可了基线会标记的某种做法，就压掉那个坏味道。
- **永远是判断，不是硬性违规。** 每个坏味道都是一个带标注的启发式判断（“可能有 Feature Envy”），绝不是硬性违规。和这里其他规范一样，工具已经强制的东西就跳过。

每个坏味道读作*它是什么* → *怎么修*；拿它对着 diff 匹配：

- **神秘命名（Mysterious Name）**：函数、变量或类型的名字看不出它做什么或装什么。→ 改名；如果起不出诚实的名字，说明设计本身模糊。
- **重复代码（Duplicated Code）**：同一段逻辑形态在改动里的多处 hunk 或多个文件里出现。→ 抽出共同的形态，从两边调用它。
- **依恋情结（Feature Envy）**：某个方法访问别的对象的数据比访问自己的还多。→ 把这个方法搬到它依恋的数据上去。
- **数据泥团（Data Clumps）**：同样的几个字段或参数总是结伴出现（一个想要诞生的类型）。→ 把它们捆成一个类型，传那个类型。
- **基本类型偏执（Primitive Obsession）**：用基本类型或字符串顶替一个值得拥有自己类型的领域概念。→ 给这个概念一个自己的小类型。
- **重复的 switch（Repeated Switches）**：针对同一类型的同一组 `switch`／`if` 级联在改动里反复出现。→ 换成多态，或者让两处共用一张映射表。
- **霰弹式修改（Shotgun Surgery）**：一次逻辑改动迫使你在 diff 里跨很多文件零散修改。→ 把一起变的东西收进一个模块。
- **发散式变化（Divergent Change）**：一个文件或模块因为几个互不相关的原因被改。→ 拆开，让每个模块只因为一个原因变化。
- **夸夸其谈通用性（Speculative Generality）**：为规格说明里并不存在的需求添加抽象、参数或钩子。→ 删掉；内联回去，直到真有需求出现。
- **过长的消息链（Message Chains）**：调用方不该依赖的 `a.b().c().d()` 长链导航。→ 把这段走查藏到第一个对象的一个方法后面。
- **中间人（Middle Man）**：一个类或函数大部分只是往下转发。→ 删掉它，直接调用真正的目标。
- **被拒绝的遗赠（Refused Bequest）**：子类或实现者忽略或覆盖掉它继承的大部分东西。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

把两个子代理调用一起发出去，放在前台，汇总它们返回的报告。

**标准子代理的提示**应当包含：

- 完整的 diff 命令和提交清单。
- 第 3 步找到的规范来源文件清单，**加上第 3 步的坏味道基线全文**（子代理没有别的途径拿到它）。
- 任务说明：“按文件／hunk 汇报相关之处：(a) diff 违反某条写明规范的每一处：引用该规范（文件 + 规则）；(b) 你发现的任何基线坏味道：说出名字并引用相应 hunk。区分硬性违规和判断类问题：违反写明规范可以是硬性的，但基线坏味道永远是判断类的，而且仓库写明的规范优先于基线。工具已经强制的东西跳过。不超过 400 词。”

**规格子代理的提示**应当包含：

- diff 命令和提交清单。
- 规格说明的路径或取回的内容。
- 任务说明：“汇报：(a) 规格说明要求但缺失或只做了一部分的条目；(b) diff 里没被要求的行为（范围蔓延）；(c) 看起来实现了、但实现看起来不对的条目。每条发现都引用规格说明原文。不超过 400 词。”

如果规格说明缺失，跳过规格子代理，并在最终报告里注明。

### 5. 汇总

把两份报告放在 `## 标准` 和 `## 规格` 两个标题下呈现，原文照用或略作整理。**不要**合并或重新排序发现，因为两条轴是有意分开的（见_为什么两条轴_）。

最后用一行总结：每条轴的发现数量，以及*每条轴内部*最严重的问题（如果有）。不要在两条轴之间挑一个总冠军：那正是这种分离要防止的重新排序。

## 为什么两条轴

一个改动可以通过一条轴而败在另一条：

- 遵守了每一条规范，但实现的东西是错的 → **标准通过，规格不通过。**
- 完全按议题要求实现，但破坏了项目的约定 → **规格通过，标准不通过。**

分开汇报能防止一条轴掩盖另一条。
