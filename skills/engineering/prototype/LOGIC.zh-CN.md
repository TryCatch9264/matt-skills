# 逻辑原型

一个自包含的单个 HTML 文件（**可分享的演示**），任何人都能点按钮驱动一个状态模型。当问题关乎**业务逻辑、状态流转或数据形态**时用它：这类东西在纸上看着合理，一旦推过真实情形才觉得不对。

因为是一个文件、什么都不用装，你可以把它交给非开发者（设计师、产品经理、领域专家），让他们自己感受这个模型。所以它说他们的语言，而不是代码的语言。

## 什么时候该用这个形态

- “我不确定这个状态机能不能处理先 X 再 Y 的那种边界情况。”
- “这个数据模型到底能不能表达……那种情形？”
- “我想在动手写之前先摸出 API 该长什么样。”
- 任何需要**按按钮并观察状态变化**的事。

如果问题是“这个应该长什么样”，那就走错了分支。用 [UI.md](UI.zh-CN.md)。

## 流程

### 1. 写明问题

写代码之前，先写下你在原型化的状态模型和要回答的问题。一段话，放在演示最上面（写在看得见的引言里，不只是注释）。回答错问题的逻辑原型是纯浪费，所以把问题写明，好让以后能核对，无论用户是当场在看还是之后脱手回来看。

### 2. 把逻辑隔离成可移植的模块

把真正的逻辑（回答问题的那些）放进单个 `<script>` 块，写成一个小而纯的模块，将来可以整体提出来放进真实代码库。它周围那一页是一次性的，这个模块不是。

正确的形态取决于问题：

- **纯 reducer**：`(state, action) => state`。动作是离散事件、状态是单个值时合适。
- **状态机**：显式的状态和迁移。“此刻哪些动作才算合法”本身就是问题的一部分时合适。
- **一组纯函数**，作用于一个普通数据类型。没有隐含的当前状态、只有转换时合适。
- **一个有清晰方法面的类或模块**：当逻辑确实拥有持续的内部控制状态时。

选最适合所问问题的形态，*不是*最容易接到页面上的形态。保持纯净：不碰 DOM、不碰 `document`，不让按钮处理函数伸进去。页面调用它，没有反向流动。这才是原型在自身寿命之外仍然有用的原因：问题答完之后，验证过的 reducer／状态机／函数组可以自行提升到真实模块里。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：不用框架、不用打包器、不用服务器，全部内联，双击就能打开，通过邮件发来发去也照样能用。任何人都应当能打开就跑。

为不写代码的人写。每个标签都用**领域语言**，不用代码：按钮和状态读起来像业务，不像 reducer。用平白的话解释正在发生什么。

自上而下，按清晰的层次布局：

1. **标题和一行说明**，讲清这个演示让你探索什么（第 1 步的问题）。
2. **当前状态**：完整的相关状态，渲染成一块可读的面板（有标签的字段，不是原始 JSON 转储），每次点击后重新渲染，让变化看得见。在有助于非开发者跟上的地方，点出刚刚变了什么。
3. **自由操作按钮**：每个动作一个按钮，始终可用，任何人都能按任意顺序摆弄模型。每次点击都派发对应动作并重新渲染状态。
4. **引导式演练**：一组**场景**，一个标签页一个。每个标签页里有对场景的简短白话描述（它设置了什么情形、该留意什么），下面是为该场景准备的**按顺序要按的按钮**。每一步都是真按钮：点击它执行该动作并前进到下一步。开始演练时重置到已知的初始状态，保证场景每次都跑得一样。

挑那些能展示棘手情形的场景，也就是在纸上难以推理的：顺路情形、刁钻的边界情况、以及一次本该非法的尝试。

要漂亮但克制：干净的排版、宽松的间距、一种强调色。不要动画，不要花招：任何会跟状态和按钮抢注意力的东西都不要。

### 4. 交出去

把文件发给他们，或者替他们打开。他们有空时会点完演练和自由操作；有意思的时刻是他们说“等等，这不该可能”或者“嗯，我以为 X 会不一样”。那些是_想法_本身的缺陷，而这正是重点。如果他们想要新的动作或新场景，就加上。原型是会演进的。

### 5. 保存答案和原型

原型回答完问题之后，先保存答案，再按 [SKILL](SKILL.zh-CN.md) 里说的方法保存原型。具体到逻辑原型：验证过的 reducer／状态机／函数组提升到真实模块里（决定被吸收）；HTML 外壳跟着上那条一次性分支，把原型作为一手资料保留下来，而且因为它只是一个自包含文件，在那个分支上随时都能重新跑起来。

## 反模式

- **不要加测试。** 需要测试的原型就不再是原型了。
- **不要接真实数据库。** 用内存状态，除非问题明确关于持久化。
- **不要做通用化。** 不要“以后想支持 X 怎么办”。原型只回答一个问题。
- **不要把逻辑和页面搅在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理函数，它就无法再被提取。让页面做纯模块之上的一层薄壳。
- **不要动用框架、打包器或服务器。** 收件人双击的就是一个文件；一个 React 应用或开发服务器会毁掉“可分享”。
- **不要把 HTML 外壳发布到生产环境。** 页面是针对手工点按优化的。它背后的逻辑模块才是值得留下的部分。
