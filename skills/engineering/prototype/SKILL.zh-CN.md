# 原型

原型是**用来回答某个问题的一次性代码**。问题的性质决定原型的形态。

## 选择分支

先确定要回答的是哪个问题，依据用户的提示、周围的代码，或者用户在场时直接询问：

- **“这套逻辑／状态模型感觉对吗？”** → [LOGIC.md](LOGIC.zh-CN.md)。做一个可分享的单个 HTML 文件（自由操作按钮，加上分标签页的引导式演练），把状态机推到那些在纸上难以推理的情形上跑一遍，并且让非开发者也能操作。
- **“这个应该长什么样？”** → [UI.md](UI.zh-CN.md)。在同一个路由上生成几个截然不同的界面版本，通过 URL 查询参数和底部浮动条切换。

两条分支产出的东西差别很大，选错就白做了整个原型。如果问题确有歧义，又联系不上用户，就选更贴近周围代码的那条分支（后端模块 → 逻辑；页面或组件 → 界面），并把这一假设写在原型最上面。

## 两条分支都适用的规则

1. **从第一天就是一次性的，而且明白标注出来。** 把原型代码放在它真正会被用到的地方附近（就在它所原型化的模块或页面旁边），这样上下文一目了然；但命名要让随手看到的读者知道这是原型而不是生成代码。对于一次性的界面路由，遵守项目已有的路由约定；不要另造一套新的顶层结构。
2. **启动要毫不费力。** 界面原型从项目任务运行器里的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等等。逻辑演示是用户双击就能打开的单个 HTML 文件。无论哪种，启动都不该需要动脑。
3. **默认不做持久化。** 状态放在内存里。持久化正是原型在*检验*的东西，不是它该依赖的东西。如果问题本身明确涉及数据库，就用一个临时数据库，或者一个名字写明“PROTOTYPE, wipe me”的本地文件。
4. **不做打磨。** 不写测试，除了让原型*跑得起来*必需的之外不写错误处理，不做抽象。目的是尽快学到东西。
5. **把状态显示出来。** 每次操作之后（逻辑原型）或每次切换版本时（界面原型），打印或渲染出完整的相关状态，让用户看到变化了什么。
6. **做完就保存下来。** 把验证过的决定并进真实代码，然后把原型本身作为**一手资料**保留下来：提交到一个一次性分支上，不进 main，并在实现议题上留下指向该分支的上下文指针。同时把答案（结论，以及它解决的是哪个问题）记在议题或某次提交里。main 分支只保留验证过的决定。
