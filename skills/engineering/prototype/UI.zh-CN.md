# 界面原型

在同一个路由上生成**几个截然不同的界面版本**，通过底部浮动条切换。用户在浏览器里来回切换版本，挑一个（或者从每个里各拿一点），然后把其余的丢掉。

如果问题关乎逻辑／状态而不是某样东西看起来怎样，那就走错了分支。用 [LOGIC.md](LOGIC.zh-CN.md)。

## 什么时候该用这个形态

- “这个页面应该长什么样？”
- “我想在定下来之前看看这个仪表盘的几个方案。”
- “给设置页试试另一种布局。”
- 任何用户本来要在脑子里对三个模糊草图纠结一天的时候。

## 两种子形态：强烈优先 A

当界面原型**紧挨着应用其余部分**时，判断起来容易得多：真实的页头、真实的侧栏、真实的数据、真实的密度。单独一条一次性路由是真空：每个版本孤立看都挺好。只要有现成页面能承载这些版本，就默认用子形态 A。只有当原型确实没有近旁的家时，才考虑子形态 B。

### 子形态 A：改造现有页面（优先）

路由已经存在。版本渲染在**同一个路由上**，用 `?variant=` URL 查询参数控制。现有的数据获取、参数和鉴权全部保留，只换渲染。这是默认做法；除非有具体理由，就选它。

如果原型针对的东西还没有页面、但*天然会住在某个页面里*（仪表盘的新区块、设置页上的新卡片、现有流程里的新步骤），它仍然属于子形态 A。把版本挂进宿主页面里。

### 子形态 B：新页面（最后手段）

只有当被原型化的东西确实没有现成页面可以安放时才用（例如一个全新的顶层界面，或者一个没法合理嵌入任何地方的流程）。

按项目已有的路由约定创建一条**一次性路由**。不要另造一套新的顶层结构。命名要让它明显是原型（例如在路径或文件名里带 `prototype` 字样）。同样用 `?variant=` 模式。

在决定采用子形态 B 之前，先验一下：真的没有现成页面可以嵌进去吗？空路由会掩盖有内容的页面本会暴露的设计问题。

两种子形态里，底部浮动条是一样的。

## 流程

### 1. 写明问题并定下数量 N

默认 **3 个版本**。超过 5 个就不再是截然不同，而开始变成噪声，所以上限就定在这。

用一行把计划写下来，写在原型所在位置或文件顶部的注释里：

> “设置页的三个版本，在现有 `/settings` 路由上通过 `?variant=` 切换。”

无论用户当场会不会提意见，这样做都有用。

### 2. 生成截然不同的版本

起草每个版本。每个都要满足：

- 页面的目的，以及它能拿到的数据。
- 项目的组件库／样式体系（TailwindCSS、shadcn、MUI、纯 CSS，随便哪种）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

版本之间必须在**结构上不同**：布局不同、信息层级不同、主要操作入口不同，而不只是颜色不同。三张稍作调整的卡片网格不是界面原型，是墙纸。如果两版起草出来太像，就重做其中一版，并明确要求“不要用卡片网格”。

### 3. 把它们接起来

在路由上创建一个切换组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对子形态 A（现有页面）：把所有现有数据获取保留在切换器之上；每次只有渲染的子树按版本变化。

对子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 做浮动切换条

屏幕底部居中的一条小浮动条，包含三部分：

- **左箭头**：切到上一个版本（循环）。
- **版本标签**：显示当前版本键，如果该版本导出了名字，也显示那个名字。例如 `B (Sidebar layout)`。
- **右箭头**：切到下一个版本（循环）。

行为：

- 点击箭头会更新 URL 查询参数（用框架自带的路由，例如 Next 的 `router.replace`、React Router 的 `navigate` 等），这样版本可以分享、刷新后保持。
- 键盘：`←` 和 `→` 方向键也能切换。当焦点在 `<input>`、`<textarea>` 或 `[contenteditable]` 上时，不要接管方向键。
- 视觉上要跟页面区分开（例如高对比的胶囊样式、轻微阴影），让人明显看出它不属于被评估的设计。
- 在生产构建里隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价判断来控制，免得某次原型误合并把这条浮动条发给用户。

把切换器做成单个共享组件，好让两种子形态复用。放在项目里共享界面代码该放的地方。

### 5. 交出去

把 URL（以及各个 `?variant=` 键）给出来。用户有空时会翻着看。有意思的反馈通常是**“我想要 B 的页头配 C 的侧栏”**，那才是他们真正想要的设计。

### 6. 保存答案并清理

某个版本胜出后，先保存答案（哪个版本、为什么），再按 [SKILL](SKILL.zh-CN.md) 里说的方法保存原型。把胜出者并进真实代码，其余的移到那条一次性分支上，不要留在 main：

- **子形态 A**：把胜出者并进现有页面；把落选的版本和切换器从 main 上删掉。
- **子形态 B**：把胜出的版本提升为真正的路由；把一次性路由和切换器从 main 上删掉。

整套版本是一手资料，所以它落到那条一次性分支上，而不是垃圾桶，因为留在 main 分支里的版本组件和切换器会很快腐坏，还会让下一个读者困惑。

## 反模式

- **只在颜色或文案上不同的版本。** 那是微调，不是原型。真正的版本在结构上有分歧。
- **版本之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就毁了意义。每个版本都应当可以自由地推翻布局。
- **把版本接到真实的写操作上。** 只读原型就很好。如果某个版本需要写数据，就指向一个桩：问题在于“这个该长什么样”，不是“后端能不能用”。
- **把原型直接提升上生产。** 版本代码是在原型约束下写的（没测试、错误处理最少）。合并回去时要好好重写。
