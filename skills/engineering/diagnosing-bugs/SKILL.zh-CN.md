# 诊断缺陷

应对难缠缺陷的一套章法。只有给出明确理由时才跳过某个阶段。

探索代码库时，读一遍 `GLOSSARY.md`（如果存在），建立相关模块的清晰心智模型，并检查你改动范围内的 ADR。

## 脱敏

这个技能会让你展示命令、输出和捕获的产物。**先对每个密钥脱敏**：把它的位置写成 `<REDACTED>`。基于环境变量搭循环，让凭据留在环境里，而不出现在你展示的内容里。捕获的产物里带鉴权头：只引用承载信号的那几行。

如果脱敏后的输出不足以诊断缺陷，就说明情况并问用户。

## 阶段 1：建立反馈回路

**这才是技能本身。** 其余都是机械活。如果你有一个针对该缺陷的**紧**的通过／失败信号（一个能对*这个*缺陷变红的信号），你就能找到原因；二分、假设检验、加观测都只是消耗它。如果没有，盯着代码看多久都救不了你。

在这里投入不成比例的精力。**要积极。要有想象力。不认输。**

### 构造回路的方式，大致按这个顺序

1. 在任何能触达缺陷的接缝上写**失败测试**：单元、集成、端到端。
2. 对运行中的开发服务器写 **curl / HTTP 脚本**。
3. **命令行调用**，配一份固定输入，把 stdout 和已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动界面并对 DOM／控制台／网络做断言。
5. **重放捕获的轨迹。** 把真实的网络请求／载荷／事件日志存到磁盘，在隔离环境里沿代码路径重放。
6. **一次性测试装置。** 起一个最小子集（一个服务、mock 掉依赖），用一次函数调用跑到缺陷所在路径。
7. **属性／模糊测试循环。** 如果缺陷是“有时输出错误”，跑 1000 个随机输入找失败模式。
8. **二分测试装置。** 如果缺陷出现在两个已知状态之间（提交、数据集、版本），把“在状态 X 启动、检查、重复”自动化，好让你能 `git bisect run`。
9. **差分循环。** 把同一输入分别跑过旧版本和新版本（或两套配置），diff 输出。
10. **人机协同 bash 脚本。** 最后手段。如果需要人来点击，就用 `scripts/hitl-loop.template.sh` 驱动*他们*，这样回路仍然是结构化的。捕获的输出再喂回给你。

搭对反馈回路，缺陷就解决了 90%。

### 把回路拧紧

把回路当成产品对待。一旦有了*一个*回路，就**拧紧**它：

- 能更快吗？（缓存初始化、跳过无关启动、缩小测试范围。）
- 信号能更锐利吗？（断言具体症状，而不是“没崩”。）
- 能更确定吗？（固定时间、固定随机种子、隔离文件系统、冻结网络。）

30 秒还不稳定的回路比没有好不了多少；2 秒且确定的回路才叫紧，是调试的超能力。

### 不确定的缺陷

目标不是干净的复现，而是**更高的复现率**。把触发跑 100 次、并行、加压、缩窄时间窗口、注入等待。50% 才出现的缺陷是能调试的，1% 不能，所以持续提高比例，直到可调试。

### 当你确实造不出回路时

停下来，明确说出来。列出你试过什么。向用户要：(a) 能复现该问题的环境的访问权，(b) 一份脱敏后的捕获产物（HAR 文件、日志转储、核心转储、带时间戳的录屏），或者 (c) 允许添加临时生产环境观测。**不要**在没有回路的情况下继续进入假设阶段。

### 完成标准：一条会变红的紧回路

阶段 1 完成的标志是回路**紧**且**能变红**：你能说出**一条命令**（脚本路径、测试调用、curl），你**已经至少运行过一次**（展示调用方式和它的输出，已脱敏），并且它满足：

- [ ] **能变红**：它跑到真正的缺陷代码路径上，并断言**用户描述的确切症状**，所以它能在该缺陷上变红、修好后变绿。不是“运行不报错”；它必须能*抓住这个具体缺陷*。
- [ ] **确定**：每次运行结论相同（不稳定的缺陷：按上面的做法固定一个较高的复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **代理可运行**：你能无人值守地运行它；需要人参与时只通过 `scripts/hitl-loop.template.sh`。

如果你发现自己在这条命令存在之前就靠读代码建理论，**停下：直接跳到假设，正是这个技能要防的失败模式。** 没有能变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

运行回路。看着它随着缺陷出现而变红。

确认：

- [ ] 回路产生的失败模式是**用户**描述的那个，而不是附近碰巧发生的另一个失败。错的问题 = 错的修复。
- [ ] 失败在多次运行中可复现（或者，对不确定的缺陷，复现率高到足以调试）。
- [ ] 你已捕获确切症状（错误信息、错误输出、缓慢的耗时），好让后续阶段验证修复确实解决了它。

### 最小化

一旦变红，把复现缩到**仍能变红的最小场景**。**一次一个**地砍掉输入、调用方、配置、数据、步骤，每砍一次重跑回路，只保留对失败起支撑作用的东西。

为什么值得做：最小复现缩小阶段 3 的假设空间（剩下的可怀疑变动更少），并在阶段 5 变成干净的回归测试。

完成标志是**剩下的每个元素都起支撑作用**：去掉任何一个，回路就变绿。

在你既复现**又**最小化之前，不要往下走。

## 阶段 3：提假设

在测试任何一个之前，先产生 **3 到 5 个排序的假设**。只产生一个假设会锚定在第一个看起来合理的想法上。

每个假设都必须**可证伪**：说出它所作出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会让缺陷消失／<改变 Z> 会让它更严重。”

如果你说不出这个预测，那这个假设只是一团感觉：丢掉或者磨尖。

**在测试之前把排序后的清单给用户看。** 他们常有能立刻重排的领域知识（“我们刚部署了第 3 项相关改动”），或者知道哪些假设已经被排除。这个检查点很便宜，能省很多时间。不要卡在这里等；用户不在时就按你的排序继续。

## 阶段 4：加观测

每个探针都必须对应阶段 3 的某个具体预测。**一次只改一个变量。**

工具偏好：

1. 环境支持就用**调试器／REPL 查看**。一个断点胜过十条日志。
2. 在能区分假设的边界处加**有目标的日志**。
3. 绝不“全打日志再 grep”。

**给每条调试日志打唯一前缀**，例如 `[DEBUG-a4f2]`。收尾清理时就变成一次 grep。没打标签的日志会活下来；打了标签的会死掉。

**性能分支。** 对性能退化，日志通常不是对的做法。改为：先建立基线测量（计时装置、`performance.now()`、分析器、查询计划），再二分。先测量，再修。

## 阶段 5：修复 + 回归测试

**在修复之前**写回归测试，但前提是存在**正确的接缝**。

正确的接缝是指测试能在调用点按缺陷实际发生的方式跑到**真实的缺陷模式**。如果唯一可用的接缝太浅（缺陷需要多个调用方，却只有单调用方测试；单元测试复现不出触发该缺陷的链路），那里的回归测试只会给出虚假的信心。

**如果没有正确的接缝，这件事本身就是一条发现。** 记下来。代码库架构妨碍了把缺陷固定住。把这点交给下一个阶段。

如果存在正确的接缝：

1. 把最小复现变成该接缝上的失败测试。
2. 看着它失败。如果你是通过改动代码或测试夹具强行造出红灯，就先和原始副本 `diff`，证明改动确实生效，再相信它。
3. 应用修复。
4. 看着它通过。
5. 对原始的（未最小化的）场景重跑阶段 1 的反馈回路。

## 阶段 6：收尾

宣布完成之前必须做到：

- [ ] 原始复现不再出现（重跑阶段 1 的回路）
- [ ] 回归测试通过（或者缺少接缝一事已记录在案）
- [ ] 所有 `[DEBUG-...]` 观测代码已移除（用前缀 `grep` 一遍）
- [ ] 一次性原型已删除（或移到明确标注的调试位置）
- [ ] 最终被证明正确的假设写在提交／PR 信息里，好让下一个调试的人学到东西
