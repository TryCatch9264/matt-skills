# 加深模块

给定一组浅模块的依赖情况，如何安全地加深它们。使用 [SKILL.md](SKILL.zh-CN.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**。

## 依赖分类

评估一个可以加深的候选时，先给它的依赖分类。类别决定了加深后的模块如何跨越接缝进行测试。

### 1. 进程内

纯计算、内存状态，没有 I/O。总是可以加深：合并模块，直接通过新接口测试。不需要适配器。

### 2. 有本地替代品

有本地测试替身的依赖（Postgres 用 PGLite，内存文件系统）。存在替身就可以加深。加深后的模块在测试套件中用替身运行来测试。接缝在内部；模块对外的接口上没有端口。

### 3. 远程但自有（端口与适配器）

你自己的服务，隔着网络边界（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深模块持有逻辑；传输层作为**适配器**注入。测试用内存适配器，生产用 HTTP/gRPC/队列适配器。

建议的措辞形式：*“在接缝处定义一个端口，为生产实现一个 HTTP 适配器，为测试实现一个内存适配器，这样即使逻辑分散部署在网络上，它也待在一个深模块里。”*

### 4. 真正的外部（Mock）

你无法控制的第三方服务（Stripe、Twilio 等）。加深后的模块把外部依赖作为注入的端口接收，测试提供 mock 适配器。

## 接缝纪律

- **一个适配器意味着假想的接缝，两个适配器才意味着真实的接缝。** 除非至少有两个适配器站得住脚（通常是生产加测试），否则不要引入端口。只有单个适配器的接缝只是多绕了一层。
- **内部接缝与外部接缝。** 一个深模块可以有内部接缝（只对它的实现可见，由它自己的测试使用），也可以有接口处的对外接缝。不要因为测试用到内部接缝，就把它们暴露到接口上。

## 测试策略：替换，而不是叠加

- 一旦在加深后的模块接口上有了测试，浅模块上的旧单元测试就成了浪费，删掉它们。
- 在加深后的模块接口上写新测试。**接口就是测试面**。
- 测试通过接口断言可观察的结果，而不是内部状态。
- 测试应当扛得住内部重构，因为它们描述的是行为，不是实现。如果一个测试在实现变化时必须跟着改，那它测到了接口之外。
