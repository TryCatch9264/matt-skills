# 代码库设计

设计**深模块**：在小接口后面放大量行为，安放在干净的接缝处，可以通过该接口测试。凡是设计或重构代码的地方，都使用这套语言和这些原则。目标是给调用方杠杆，给维护者局部性，给所有人可测试性。

## 术语表

严格使用这些术语：不要替换成“组件”“服务”“API”或“边界”。语言一致本身就是目的。

**模块（Module）**：任何同时具有接口和实现的东西。有意做成与规模无关：一个函数、类、包，或者横跨多个层的切片。_避免_：单元、组件、服务。

**接口（Interface）**：调用方为了正确使用模块所必须知道的一切：类型签名，也包括不变量、顺序约束、错误模式、必要的配置和性能特征。_避免_：API、签名（都太窄，它们只指类型层面的表面）。

**实现（Implementation）**：模块内部的东西，它的代码主体。与**适配器**不同：一个东西可以是实现很大的小适配器（一个 Postgres 仓储），也可以是实现很小的大适配器（一个内存中的假实现）。接缝是话题时用“适配器”，其他情况用“实现”。

**深度（Depth）**：接口处的杠杆。调用方（或测试）每学习一单位接口所能行使的行为量。大量行为藏在小接口后面时，模块是**深**的；接口几乎和实现一样复杂时，是**浅**的。

**接缝（Seam）** _（Michael Feathers）_：可以在不修改该处代码的情况下改变行为的地方；模块接口所在的*位置*。接缝放在哪里本身就是一个设计决定，与它后面放什么相互独立。_避免_：边界（与 DDD 的限界上下文混用）。

**适配器（Adapter）**：在接缝处满足某个接口的具体东西。描述的是*角色*（占哪个位置），不是实质（里面是什么）。

**杠杆（Leverage）**：调用方从深度中得到的东西。每学习一单位接口换来更多能力。一份实现回报在 N 个调用点和 M 个测试上。

**局部性（Locality）**：维护者从深度中得到的东西。改动、缺陷、知识和验证集中在一处，而不是散落到各个调用方。改一次，处处都改好。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（要避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

设计接口时问自己：

- 我能减少方法的数量吗？
- 我能简化参数吗？
- 我能把更多复杂度藏到里面吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部可以由小的、可 mock 的、可替换的部件组成；它们只是不属于接口。模块既可以有**内部接缝**（只对它自己的实现可见，由它自己的测试使用），也可以在接口处有**外部接缝**。
- **删除测试。** 设想把这个模块删掉。如果复杂度消失了，它就是个通道。如果复杂度在 N 个调用方上重新出现，它就值回票价。
- **接口就是测试面。** 调用方和测试穿过同一个接缝。如果你想*绕过*接口去测试，说明模块的形状多半不对。
- **一个适配器意味着假想的接缝，两个适配器才意味着真实的接缝。** 除非确实有东西在接缝两侧变化，否则不要引入接缝。

## 为可测试性设计

好接口让测试变得自然：

1. **接收依赖，不要自己创建。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面积要小。** 方法更少 = 需要的测试更少。参数更少 = 测试准备更简单。

## 关系

- 一个**模块**恰好有一个**接口**（它呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，相对于它的**接口**来度量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**位于**接缝**处并满足该**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 被否掉的表述

- **把深度当作实现行数与接口行数的比值**（Ousterhout）：这会奖励往实现里掺水。我们改用“深度即杠杆”。
- **把“接口”理解为 TypeScript 的 `interface` 关键字或类的公开方法**：太窄：这里的接口包含调用方必须知道的每一个事实。
- **“边界”**：与 DDD 的限界上下文混用。请说**接缝**或**接口**。
