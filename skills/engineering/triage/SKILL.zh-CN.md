# 分诊

让项目议题跟踪器上的议题沿一个小型的分诊角色状态机流转。

如果这个仓库把外部拉取请求视为需求入口（见议题跟踪器配置），分诊也覆盖它们：**一个 PR 就是附带代码的议题**，使用同样的角色、同样的状态和同一台状态机，只有几处差异，下面用“对 PR 而言”标出。光写 `#42` 时，按跟踪器配置判断它指的是议题还是 PR。

分诊期间在议题跟踪器上发布的每条评论或议题，**必须**以这段声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.zh-CN.md)：怎么写一份能长期使用的代理说明
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.zh-CN.md)：`.out-of-scope/` 知识库怎么运作

## 角色

两个**分类**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：等报告者补充信息
- `ready-for-agent`：规格完整，可以交给脱手的代理
- `ready-for-human`：需要人来实现
- `wontfix`：不会处理

对 PR 而言，同样的状态对着附带的代码来读：`ready-for-agent` 表示已经附上说明，代理应当在这个 diff 上推进下一步；`ready-for-human` 表示可以交给人合并了。

每条分诊过的议题都应当恰好带一个分类角色和一个状态角色。如果状态角色互相冲突，就提出来并先问维护者，再做别的事。

这些是标准的角色名。议题跟踪器里实际使用的标签字符串可能不同。映射关系应当已经提供给你。如果没有，让用户运行 `/setup-matt-pocock-skills`。

状态迁移：没有标签的议题通常先去 `needs-triage`；从那里再移到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者可以随时覆盖；遇到看起来不寻常的迁移，先提出来问再动手。

## 调用方式

维护者调用 `/triage`，用自然语言说明想要什么。理解请求并执行。例如：

- “给我看看有什么需要我处理的”
- “我们看看 #42”（议题或 PR）
- “把 #42 移到 ready-for-agent”
- “有什么是代理可以接手的？”

## 展示需要处理的东西

查询议题跟踪器，分三组呈现，最旧的在前：

1. **无标签**：从没分诊过。
2. **`needs-triage`**：正在评估。
3. **`needs-info` 且自上次分诊记录以来报告者有活动**：需要重新评估。

PR 在范围内时，把这些外部 PR 也放进这几组，并在每行标注 `[PR]` 或 `[issue]`。发现阶段只列出*外部* PR（谁算外部由跟踪器配置定义），所以协作者正在处理的 PR 不算分诊工作。这个过滤只用于发现；被明确点名的 PR 无论作者是谁都要分诊。

显示数量，并给每项一行摘要。让维护者挑。

## 分诊某个具体议题或 PR

1. **收集上下文。** 读完整的议题或 PR（正文、评论、标签、作者、日期；PR 还要看 diff）。解析已有的分诊记录，避免重复询问已经解决的问题。用项目的领域术语表探索代码库，遵守相关范围的 ADR。对代码库做两项检查：(a) **重复**：按领域概念（不只是请求里的措辞）搜索是否已有该行为的实现，并报告你查过的地方。如果找到，这就是已实现的 `wontfix`（第 5 步）。(b) **先前否决**：读 `.out-of-scope/*.md`，把与此请求相似的文件摆出来。

2. **给建议。** 告诉维护者你建议的分类和状态，附上理由，并给出与该请求相关的简要代码库概况（包括它是否已经实现）。等指示。

3. **验证说法。** 任何拷问之前，先确认这个说法站得住。对缺陷，按报告者的步骤复现。对 PR，确认 diff 确实做了它声称的事：检出代码，运行相关测试或命令。报告结果：已确认（附代码路径）、未通过，或者细节不足（这是很强的 `needs-info` 信号）。验证通过能让代理说明强得多。

4. **拷问（如需要）。** 如果请求需要充实，调用 Skill 工具两次，分别运行 `grilling` 和 `domain-modeling`，一轮问题一轮问题地把它拷问成形，磨利领域术语，并在决定落定时就地更新 `GLOSSARY.md`／ADR。

5. **落实结论：**
   - `ready-for-agent`：发布一条代理说明评论（[AGENT-BRIEF.md](AGENT-BRIEF.zh-CN.md)）。
   - `ready-for-human`：结构和代理说明一样，但注明为什么不能委派出去（判断类决定、外部访问、设计决定、手工测试）。
   - `needs-info`：发布分诊记录（模板见下）。
   - 对 `wontfix`，关闭议题，评论内容取决于*原因*：
     - **已经实现**：改动已经存在于代码库中。指出它在哪里；**不要**写进 `.out-of-scope/`（那个知识库是给*被否掉*的请求用的，不是给已建好的）。
     - **否决（缺陷）**：礼貌说明理由，然后关闭。
     - **否决（功能增强）**：写进 `.out-of-scope/`，在评论里链接过去，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.zh-CN.md)）。
   - `needs-triage`：打上该角色。如果有部分进展，可选地留一条评论。

## 快速覆盖状态

如果维护者说“把 #42 移到 ready-for-agent”，就信他，直接打上该角色。先确认你打算做什么（改角色、评论、关闭），再动手。跳过拷问。如果没做拷问就直接移到 `ready-for-agent`，问他们要不要写一份代理说明。

## needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把拷问过程中解决的所有事情记到“目前已确认”下面，免得工作丢失。问题必须具体、可执行，不能写“请提供更多信息”。

## 恢复之前的会话

如果议题或 PR 上已有分诊记录，读一遍，看报告者是否回答了未解决的问题，并在继续之前给出更新后的全貌。不要重复询问已经解决的问题。
