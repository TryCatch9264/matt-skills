一个松散的想法来了，大到一次代理会话装不下，而且裹在迷雾里：从这里到**目的地**的路还看不见。寻路要做的就是找到这条路，而不是朝目的地硬冲。这个技能把路画成仓库议题跟踪器上的一张**共享地图**，然后逐个处理它的**决策工单**（解决结果是某个决定的问题，而不是要执行的构建切片），直到路线清晰。

目的地因事而异，而说出它就是画图的第一件事：它决定每张工单的形状。它可能是一份要交出去反复迭代的规格说明，可能是规划开始前要先定下的一个决定，也可能是原地做的改动，比如数据结构迁移。地图与领域无关：工程工作、课程内容，什么形态合适都行。

## 只规划，不动手

寻路默认是**规划**：每张工单解决一个决定，等路清晰时就完成地图，在有人真正动手之前不再剩下要决定的东西。想直接去干活的冲动，通常正是你已经到达地图边缘、该交接的信号。某项工作可以在它的**Notes**里覆盖这一点，把执行也带进地图本身，但除此之外，产出决定，不产出交付物。

## 用名字指代

每张地图和每张工单都是议题，所以它有**名字**：它的标题。在人读的所有内容里（叙述、地图的“目前的决定”），都用名字指代它，绝不用光秃秃的 id、编号或 slug。满墙 `#42, #43, #44` 读不下去；名字一眼可读。id 和 URL 不会消失；名字包住它的链接，但它们待在名字*里面*，绝不顶替名字。

## 地图

地图是本仓库议题跟踪器上的一条议题，标签为 `wayfinder:map`，是权威产物。它的工单是地图的子议题。

地图是**索引**，不是仓库。它列出已做的决定，并指向承载细节的工单；一个决定只存在一个地方，也就是它的工单，所以地图从不复述它，只做摘要并链接。

**地图、子工单、阻塞和前沿查询在物理上放在哪里，由跟踪器决定。** 议题跟踪器应当已经提供给你。如果没有，让用户运行 `/setup-matt-pocock-skills`。查阅跟踪器文档的“寻路操作”一节，看*这个*仓库怎么表达它们。如果没提供任何跟踪器，默认用本地 Markdown 跟踪器。

### 地图正文

以低分辨率呈现整张地图，每会话加载一次。未关闭的工单**不**列出来：它们是未关闭的子议题，靠查询获得。

```markdown
## Destination

<what reaching the end of this map looks like: the spec, decision, or change this effort is finding its way to. One or two lines; every session orients to it before choosing a ticket.>

## Notes

<domain; skills every session should consult; standing preferences for this effort>

## Decisions so far

<!-- the index: one line per closed ticket, enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [<closed ticket title>](link): <one-line gist of the answer>

## Not yet specified

<!-- see "Fog of war": in-scope fog you can't ticket yet; graduates as the frontier advances -->

## Out of scope

<!-- see "Out of scope": work ruled beyond the destination; closed, never graduates -->
```

### 工单

每张工单都是地图的**子议题**；跟踪器的议题 id 就是它的身份。正文就是那个问题，大小控制在一个 100K token 的代理会话内：

```markdown
## Question

<the decision or investigation this ticket resolves>
```

每张工单带一个 `wayfinder:<type>` 标签，取 `research`、`prototype`、`grilling`、`task` 之一（见 [工单类型](#工单类型)）。`wayfinder:` 标签是地图及其工单携带的唯一标签，绝不带 `ready-for-agent` 之类的分诊标签：它们是决定，不是实现工作。

一个会话在**动手之前先**把工单**领取**掉，指派给驱动这张地图的开发者，这样并发会话会跳过它。那个被指派人*就是*领取：未关闭、无人指派的工单就是没人领的。

阻塞使用跟踪器的**原生**依赖关系：这一点很重要，因为它让前沿在跟踪器自己的界面里*可视化*呈现，人不必打开地图就能看到什么可以拿。只有缺少原生阻塞的跟踪器才退回正文约定。当所有阻塞它的工单都关闭时，工单就**解除阻塞**；**前沿**就是未关闭、未阻塞、未被领取的子议题，也就是已知世界的边缘。

答案不属于正文；它在解决时被记录下来（见[推进地图](#推进地图)）。解决工单期间产生的资产从议题里链接过去，不要粘贴进来。

## 工单类型

每张工单要么是 **HITL**（人在环路里，和一个自己会说话的人*一起*做），要么是 **AFK**（代理独自驱动）。HITL 工单只通过那场现场交流解决；代理绝不代替人的那一半（一个自问自答的拷问代理就已经违反了这一点）。

- **研究（Research）**（AFK）：读文档、第三方 API 或本地资源（如知识库），找出某个决定所等的事实。由调用 Skill 工具运行 `research` 的子代理解决。需要当前工作目录之外的知识时使用。
- **原型（Prototype）**（HITL）：通过调用 Skill 工具运行 `prototype`，做一个便宜、粗糙、具体的产物（大纲、粗略版本、桩代码，或者界面／逻辑代码）来提升讨论的具体程度。把原型作为资产链接进来。“它该长什么样”或“它该怎么表现”是关键问题时使用。
- **拷问（Grilling）**（HITL）：对话。默认情形。总是调用 Skill 工具两次，分别运行 `grilling` 和 `domain-modeling`。
- **任务（Task）**（HITL 或 AFK）：在做出*决定*之前必须发生的手工工作：没什么可决定、可原型化或可研究，但讨论被它挡住。注册一个服务以便判断它的 API、开通访问权限、搬运数据以便看清它的形态。这是唯一*动手做*而不是决定的类型，它的价值来自解除某个决定的阻塞，而不是交付目的地。代理能独自驱动的就独自驱动（AFK）；否则给人一份精确的清单（HITL）。工作完成即解决；答案记录做了什么以及后续工单依赖的产生事实（凭据位置、新 URL、行数）。

## 战争迷雾

地图是*有意*不完整的：还没看到的东西就不要画。在未关闭的工单之外是**战争迷雾**：对即将到来、但还定位不了的决策与调查的模糊视野，因为它们挂在尚未解决的问题上。解决一张工单会清掉它前方的迷雾，把现在能说清的东西逐张升级成新工单，一次一张，直到通往目的地的路清晰、不再剩工单。

地图的 **Not yet specified** 一节就是写下那团模糊视野的地方：怀疑的问题、以后要回头看的区域。它是通往目的地的尚未发现的前沿：这里的一切都在范围内，只是还不够清晰到能开成工单。视野允许写多松就多松，允许写多全就多全；它同时也是给协作者的指示牌，让他们看到这项工作正往哪走。

**是迷雾还是工单？** 判据是现在能不能把问题说精确，*不是*现在能不能答出来。

- **能开成工单**指问题已经锐利，即使它被阻塞、你还动不了它。
- **放进 Not yet specified** 指你还说不了那么锐利。不要把迷雾预先切成工单大小的碎块：它比工单粗，等前沿推进到那里，一块可能升级成好几张工单，也可能一张都不生。

**Not yet specified** 不包含已经决定的（Decisions so far）、已经是未关闭工单的，以及不在范围内的（下一节）。

## 不在范围内

迷雾只朝目的地聚集。目的地固定了范围，所以超出它的工作**不在范围内**：它不是迷雾，也不属于 **Not yet specified**。它在地图上单独有一节 **Out of scope**：你已经有意识地排除在*这次*工作之外的东西。决定它归属的是范围，不是清晰度。

不在范围内的工作永远不会升级（前沿止于目的地），所以只有当目的地被重新划定它才会回来，而且那时是一次全新的工作，不是接着做。

把某件事排除在范围之外是一个划定范围的动作，不是路线上的一个步骤。当某张已经存在的工单被发现落在目的地之外（画图时误划进来，或者解决过程中暴露出来），就**关闭它**（已关闭的工单明确地不在前沿上），并在 **Out of scope** 一节留一行：摘要加为什么不在范围内，链接那张已关闭的工单。它不进 **Decisions so far**，那里记录的是实际走过的路线；范围边界不是路线上的一个步骤。

## 调用方式

两种模式。无论哪种，**每会话绝不解决超过一张工单**，研究工单除外。

### 画地图

用户带一个松散的想法调用。

1. **说出目的地。** 调用 Skill 工具两次，分别运行 `grilling` 和 `domain-modeling`，把这个地图要通往的东西定下来：规格说明、决定，还是改动。目的地固定范围，所以它最先定。
2. **摸清前沿。** 再拷问一次，这次**广度优先**：在整个空间里铺开，而不是在任一条线上深挖，把尚未解决的决定和现在就能迈出的第一步摆出来。**如果这一步没摸出任何迷雾**（通往目的地的路已经清楚，整段旅程小到一个会话就能装下），就不需要地图。停下来问用户想怎么推进。
3. **创建地图**（标签 `wayfinder:map`）：填好 Destination 和 Notes，Decisions so far 留空，把迷雾勾进 **Not yet specified**。
4. **创建现在能说清的工单**，作为地图的子议题，然后在**第二轮**里连上阻塞关系（议题要先有 id 才能互相引用）。交叉引用也在那一轮里用真实 id 写：占位的 `#<n>` 会自动链接到一条无关议题。连好之后，它们就分到了前沿和被阻塞区；还不能说清的一切留在迷雾里，也就是 **Not yet specified** 一节。
5. **启动研究子代理。** 对你刚创建的每张 `research` 工单，用全新的上下文窗口起一个子代理，调用 Skill 工具运行 `research` 并行解决它，把发现记在一次性 `research/<name>` 分支上，并从工单给出上下文指针。推送该分支但不开 PR：它永远不会被合并。
6. 停止：画地图是一个会话的工作；它不顺手解决任何东西。

### 推进地图

用户带一张地图（URL 或编号）调用。工单是**可选的**：没给工单时，由你挑下一个决定，而不是用户挑。

1. 加载**地图**：低分辨率视图，不是每张工单的正文。
2. 选工单。用户点了名就用它。否则按顺序取前沿上的第一张。**领取它**：动手之前先指派给自己。
3. 按它 `wayfinder:<type>` 标签指明的类型解决（见[工单类型](#工单类型)）。读标签，不只看正文：正文从不写类型。**按需拉近**：需要时取回任何相关或已关闭工单的完整正文；`## Notes` 块里点了名的技能，调用 Skill 工具运行。有疑问时就调用 Skill 工具两次，分别运行 `grilling` 和 `domain-modeling`。
4. 记录解决结果：把答案作为**解决评论**发布，**关闭**议题，并往地图的 Decisions so far **追加一个上下文指针**。
5. 添加新浮现的工单（先创建再连线）；把答案使其变得能说清的迷雾升级成工单，并从 **Not yet specified** 里清掉每一块已升级的内容，让它只作为新工单存在。如果答案显示某张工单（这张或别的）落在目的地之外，就**把它排除在范围之外**，而不是在路线上解决它。如果这个决定让地图其他部分失效，更新或删除那些工单。

用户可能会并行跑未阻塞的工单，所以要预期其他会话在同时编辑跟踪器。
