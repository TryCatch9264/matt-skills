# ADR 格式

ADR 放在 `docs/adr/` 下，按顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

按需创建 `docs/adr/` 目录：只有需要第一条 ADR 时才建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这些。一条 ADR 可以只有一段话。它的价值在于记下*做过*某个决定以及*为什么*，而不在于把各个小节填满。

## 可选小节

只有确实有价值时才加。多数 ADR 用不上。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决定会被重新拿出来讨论时有用
- **考虑过的选项**：只有当被否掉的方案值得记住时才写
- **后果**：只有下游存在不明显的连带影响需要点明时才写

## 编号

扫描 `docs/adr/` 找出已有的最大编号，加一。

## 什么时候提议写 ADR

下面三条必须同时成立：

1. **难以撤销**：以后改主意的代价是实打实的
2. **缺少上下文会让人意外**：将来的读者看到代码会想“他们当初到底为什么这么做？”
3. **是真实取舍的结果**：确实有别的方案，而你出于具体理由选了这一个

如果决定容易撤销，就别写：你直接改掉就行了。如果它不让人意外，没人会追问原因。如果根本没有别的方案，那除了“我们选了显而易见的那条路”，也没什么可记的。

### 什么算数

- **架构形态。** “我们用一个 monorepo。”“写模型采用事件溯源，读模型投影到 Postgres。”
- **限界上下文之间的集成方式。** “Ordering 和 Billing 通过领域事件通信，不走同步 HTTP。”
- **带锁定效应的技术选型。** 数据库、消息总线、身份认证服务商、部署目标。不是每个库都要写：只写换掉它要花一个季度的那些。
- **边界与范围决策。** “客户数据归 Customer 上下文所有，其他上下文只按 ID 引用。”明确不要什么，和明确要什么一样有价值。
- **有意偏离显而易见做法的地方。** “我们不用 ORM，改用手写 SQL，因为 X。”凡是讲道理的读者会默认相反做法的事情都算。这类记录能拦住下一位工程师去“修复”本来就是故意的东西。
- **代码里看不出来的约束。** “因为合规要求，我们不能用 AWS。”“因为和合作方 API 的约定，响应时间必须低于 200ms。”
- **原因不明显的被否方案。** 如果你考虑过 GraphQL，出于某些细微理由选了 REST，就记下来；否则半年后有人又会提议上 GraphQL。
