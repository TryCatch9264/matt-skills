# 领域建模

在设计过程中主动建立并磨利项目的领域模型。这是一项*主动的*功课：质疑用词、构造边界场景，并在术语和决定一旦成形的当下就把术语表和决定写下来。（仅仅为了取词汇而*读* `GLOSSARY.md` 不算这个技能：那只是任何技能都能顺手做的一件事。这个技能用于你正在改变模型，而不只是使用它的时候。）

## 文件结构

多数仓库只有一个上下文：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果仓库根目录有 `GLOSSARY-MAP.md`，说明仓库有多个上下文。这张图指向每个上下文所在的位置：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← system-wide decisions
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← context-specific decisions
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

按需创建文件：只有东西要写时才建。如果还没有 `GLOSSARY.md`，在第一个术语定下来的再建。如果还没有 `docs/adr/`，在需要第一条 ADR 时再建。

## 会话过程中的做法

### 对照术语表质疑

当用户用的词与 `GLOSSARY.md` 里已有的说法冲突时，立刻指出来。“你的术语表把‘取消’定义为 X，但你说的似乎是 Y。到底是哪个？”

### 磨利含糊的说法

当用户用词含糊或含义过多时，提出一个精确的统一术语。“你说的‘账户’，指的是 Customer 还是 User？这是两回事。”

### 讨论具体场景

讨论领域关系时，用具体场景给它施压。构造能碰到边界的情形，迫使用户把概念之间的边界说清楚。

### 与代码对照

用户说明某个东西怎么运作时，去核对代码是否一致。如果发现矛盾，就摆出来：“你的代码取消的是整个 Order，但你刚说部分取消是可能的。哪个是对的？”

### 就地更新 GLOSSARY.md

一个术语定下来，就当场更新 `GLOSSARY.md`。不要攒着批量做：发生一件就记一件。使用 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.zh-CN.md) 里的格式。

`GLOSSARY.md` 里应当完全没有实现细节。不要把 `GLOSSARY.md` 当成规格说明、草稿纸，或者存放实现决定的地方。它就是一份术语表，仅此而已。

### 谨慎地提议写 ADR

只有当下面三条同时成立时，才提议创建 ADR：

1. **难以撤销**：以后改主意的代价是实打实的
2. **缺少上下文会让人意外**：将来的读者会想“他们为什么这么做？”
3. **是真实取舍的结果**：确实有别的方案，而你出于具体理由选了这一个

三条里缺任何一条，就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.zh-CN.md) 里的格式。
