# 改进代码库架构

把架构上的摩擦暴露出来，并提出**加深机会**：把浅模块变成深模块的重构。目标是可测试性和 AI 可导航性。

这个命令_受_项目领域模型_启发_，并建立在一套共同的设计词汇之上：

- 调用 Skill 工具运行 `codebase-design`，取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、“接口就是测试面”、“一个适配器 = 假想的接缝，两个 = 真实的接缝”）。每条建议都严格使用这些词，不要滑向“组件”“服务”“API”或“边界”。
- `GLOSSARY.md` 里的领域语言为好接缝提供命名；`docs/adr/` 里的 ADR 记录了本命令不该重新争辩的决定。

## 流程

### 1. 探索

**扫描之前先定范围：YAGNI。** 加深模块的回报在于让将来对这个模块的改动更容易，所以要把额外的注意力放在最近改动过的代码上。先决定*在哪里*看，再去看：

- 如果用户点了方向（某个模块、某个子系统、某个痛点），就照它来，跳过下面的推断。
- 否则往回翻一段够长的提交历史（`git log --oneline`），找出代码库的热点，也就是反复出现的文件和区域，让这些路径先吸引你的注意。如果改动分散、没有明显热点，就把范围放宽。

先读项目的领域术语表（`GLOSSARY.md`）和你改动范围内的 ADR。

然后用全新的上下文窗口启动一个子代理，让它走一遍代码库。不要套死板的规则；有机地探索，并记下你在哪里感到摩擦：

- 哪里理解一个概念需要在许多小模块之间来回跳？
- 哪里的模块是**浅**的，接口几乎和实现一样复杂？
- 哪里为了可测试性单独抽出了纯函数，但真正的缺陷藏在它们的调用方式里（缺少**局部性**）？
- 哪里紧耦合的模块跨接缝泄漏？
- 代码库哪些部分没有测试，或者通过现有接口很难测试？

对你怀疑是浅的东西应用**删除测试**：删掉它是会集中复杂度，还是只是把复杂度挪走？“是的，会集中”才是你想要的信号。

### 2. 用 HTML 报告呈现候选

把一份自包含的 HTML 文件写到系统临时目录，这样仓库里不会留下东西。临时目录从 `$TMPDIR` 取，取不到就用 `/tmp`（Windows 上是 `%TEMP%`），写到 `<tmpdir>/architecture-review-<timestamp>.html`，保证每次运行都是新文件。为用户打开它（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），并告诉他绝对路径。

报告通过 CDN 引入 **Tailwind** 做布局和样式，通过 CDN 引入 **Mermaid** 来画那些用图／流程／时序能可靠说明结构的图。Mermaid 和手工 CSS/SVG 混着用：关系呈图状时（调用图、依赖、时序）用 Mermaid，想要更有编辑感的东西时（质量图、剖面图、折叠动画）用自己搭的 div/SVG。每个候选都配一张**改前／改后可视化**。要够视觉化。

每个候选渲染成一张卡片，包含：

- **文件**：涉及哪些文件／模块
- **问题**：当前架构为什么造成摩擦
- **方案**：用平实的语言描述会改什么
- **收益**：用局部性和杠杆来解释，以及测试会怎么改善
- **改前／改后图**：并排、手工绘制，展示原来的浅和加深后的样子
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 之一，渲染成徽标

报告结尾放一节**首选建议**：你会先做哪个候选，为什么。

**领域词用 GLOSSARY.md 的词汇，架构词用 `/codebase-design` 的词汇。** 如果 `GLOSSARY.md` 定义了“Order”，就说“Order 录入模块”，而不是“FooBarHandler”，也不是“Order 服务”。

**与 ADR 冲突**：如果某个候选与已有 ADR 矛盾，只有当摩擦确实严重到值得重新讨论那条 ADR 时才提出来。在卡片里明确标注（例如一段警告提示：_“与 ADR-0007 矛盾，但值得重新打开，因为……”_）。不要把 ADR 禁止的每一种理论上的重构都列出来。

完整的 HTML 骨架、图形模式和样式指引见 [HTML-REPORT.md](HTML-REPORT.zh-CN.md)。

还不要提出接口方案。文件写完后，问用户：“你想深入其中哪一个？”

### 3. 拷问循环

用户选定一个候选后，调用 Skill 工具运行 `grilling`，和他们一起走决策树：约束、依赖、加深后模块的形态、接缝背后有什么、哪些测试能留下来。

决定一旦成形，就顺手做相应的事；过程中调用 Skill 工具运行 `domain-modeling`，让领域模型保持最新：

- **用 `GLOSSARY.md` 里没有的概念给加深后的模块命名？** 把该术语加进 `GLOSSARY.md`。文件不存在时按需创建。
- **对话过程中磨利了某个含糊术语？** 当场更新 `GLOSSARY.md`。
- **用户以站得住脚的理由否掉了某个候选？** 提议写一条 ADR，措辞可以是：_“要不要我把这个记成 ADR，免得将来的架构审查又提一遍？”_ 只有当将来的探索者确实需要这条理由来避免重复建议时才提议；临时理由（“现在不值得做”）和不言自明的理由都跳过。
- **想为加深后的模块探索不同的接口方案？** 调用 Skill 工具运行 `codebase-design`，用它的“设计两次”并行子代理做法。
