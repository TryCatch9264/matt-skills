# 技能的机制

[`writing-for-agents`](SKILL.zh-CN.md) 中专门讨论技能的那一支：当文档是一个技能时，有哪些地方不同（frontmatter、调用方式的选择、路由技能）。其余关于写文档的内容，都在 `SKILL.md` 这份通用参考里。

## 调用方式

两个选择，交换的是两种负担：

- **模型调用**的技能保留 `description`，这样 agent 能自主触发它，其他技能也能找到它。你依然可以输入它的名字：模型调用始终_包含_用户可达；description 只会额外带来 agent 发现能力，从不剥夺人的入口。description 是这个技能的顶层上下文指针，被强制一直加载：用长期占用的上下文换取可被发现性。一个内容全是参考资料的模型调用技能，也是共享资料的一个落脚点：其他技能可以调用它，于是多个技能都需要的资料只存一处。机制上：不写 `disable-model-invocation`，并写一段面向模型的 description，带上各个触发分支（`SKILL.md` 里关于写指针的规则全部适用）。
- **用户调用**的技能把 description 从 agent 的可达范围里去掉：只有人输入它的名字才能触发，其他任何技能都触发不了。上下文占用为零，但消耗认知负担：你就是那个必须记得它存在的索引。机制上：设置 `disable-model-invocation: true`；`description` 变成面向人的：一行摘要，去掉触发词列表。

只有当 agent 必须自己找到这个技能，或别的技能必须找到它时，才选模型调用。如果它永远只由人手动触发，就做成用户调用，不必付出上下文占用。

两个用户调用的技能都需要的共享资料，放在两者里都不行：它们没有 description，谁也触发不了谁。把它推到技能系统之外的普通文件里：一份任何技能都能指向的外部资料。

## 按调用方式拆分

拆分中的调用方式切法（按顺序的切法在 `SKILL.md` 里）：当你有一个独立的引导词、应当能自行触发这个技能（一个你在提示里真的会用的触发词），或者别的技能必须找到它时，就拆出一个模型调用的技能。你为新加的、一直加载的 description 付出上下文占用，所以这份独立可达性必须值得。

## 路由技能

当用户调用的技能多到你记不住时，这份堆积起来的认知负担由**路由技能**解决：一个用户调用的技能，点名其他技能以及各自什么时候用，于是人只需要记住一个技能，而不是很多个。它只能给出提示，永远无法触发它们：用户调用的技能没有 description，除了人以外什么都到不了它们。
